### 1. 프로토콜의 3가지 요소

프로토콜은 통신하는 장치들이 데이터를 주고받기 위해 정한 규칙이다.

| 요소 | 의미 | 기억할 표현 |
| --- | --- | --- |
| 구문: Syntax | 데이터의 형식, 구조, 필드 배치, 부호화 방식 | 어떤 형식으로 보내는가 |
| 의미: Semantics | 각 필드의 의미와 수신 후 처리 방법, 제어·오류 처리 규칙 | 무슨 뜻이며 어떻게 처리하는가 |
| 타이밍: Timing | 전송 시점, 순서, 속도 조절 | 언제, 어떤 속도로 보내는가 |
### 2. OSI 7계층과 TCP/IP

OSI는 통신 기능을 7개 계층으로 나눈 참조 모델이고, TCP/IP는 인터넷 통신에서 사용하는 프로토콜 체계다.

| OSI 계층 | 핵심 역할 | 대표 예시 | TCP/IP 대응 |
| --- | --- | --- | --- |
| L7 응용 | 사용자 프로그램에 네트워크 서비스 제공 | HTTP, DNS, SMTP, FTP | 응용 |
| L6 표현 | 데이터 형식 변환, 압축, 암호화 | 문자 인코딩, 데이터 표현 변환 | 응용 |
| L5 세션 | 통신 세션 설정·관리·종료, 동기화 | 대화·세션 관리 | 응용 |
| L4 전송 | 응용 프로그램 사이의 데이터 전달 | TCP, UDP | 전송 |
| L3 네트워크 | IP 주소 기반 경로 선택과 패킷 전달 | IP, ICMP, 라우터 | 인터넷 |
| L2 데이터링크 | 같은 링크에서 프레임 전달, MAC 주소 사용, 오류 검출 | 이더넷, 스위치, 브리지 | 네트워크 접근 |
| L1 물리 | 비트를 전기·광·무선 신호로 전송 | 케이블, 리피터, 허브 | 네트워크 접근 |

```
OSI 7·6·5 → TCP/IP 응용
OSI 4     → TCP/IP 전송
OSI 3     → TCP/IP 인터넷
OSI 2·1   → TCP/IP 네트워크 접근
```

전송 계층의 모든 프로토콜이 신뢰성을 보장하는 것은 아니다. TCP는 재전송·순서 제어 등을 제공하지만, UDP는 자체적으로 이를 보장하지 않는다.

### 3. 계층별 데이터 단위와 주소

PDU는 각 계층에서 다루는 데이터 단위다.

| 계층 | 데이터 단위 | 주요 식별 정보 | 역할 |
| --- | --- | --- | --- |
| 응용 | 메시지·데이터 | 서비스에 따른 이름·식별자 | 전달할 내용 |
| 전송 | TCP 세그먼트 / UDP 데이터그램 | 포트 번호 | 어느 통신 종단에 전달할지 구분 |
| 네트워크 | 패킷 | IP 주소 | 어느 호스트·인터페이스로 보낼지 판단 |
| 데이터링크 | 프레임 | MAC 주소 | 현재 링크에서 누구에게 전달할지 판단 |
| 물리 | 비트 | — | 실제 신호 전송 |

| 식별 정보 | 크기 |
| --- | --- |
| TCP·UDP 포트 번호 | 16비트 |
| IPv4 주소 | 32비트 |
| IPv6 주소 | 128비트 |
| 일반적인 이더넷 MAC 주소 | 48비트 |

```
IP 주소   → 목적지 호스트
포트 번호 → 목적지 호스트 내부의 통신 종단
MAC 주소  → 현재 링크에서 전달할 상대
```

여기서 MAC은 매체 접근 제어를 뜻하며, 암호학의 메시지 인증 코드 MAC과는 다른 용어다.

### 4. 허브·스위치·라우터

| 장비 | 계층 | 전달 기준 | 핵심 동작 |
| --- | --- | --- | --- |
| 허브·리피터 | L1 | 주소를 판단하지 않음 | 신호를 재생·전달 |
| L2 스위치·브리지 | L2 | 목적지 MAC 주소 | MAC 주소 테이블을 보고 프레임 전달 |
| 라우터·L3 스위치 | L3 | 목적지 IP 주소 | 라우팅 테이블을 보고 다음 경로 결정 |
| L4 장비 | L4 정보 활용 | IP·포트 등 | 연결 단위 트래픽 분산 등에 사용 |
| L7 장비 | L7 정보 활용 | HTTP 등 응용 데이터 | URL·요청 내용 등을 기준으로 처리 |

스위치의 핵심 동작:

- 수신 프레임의 출발지 MAC 주소로 어느 포트에 어떤 장치가 있는지 학습한다.
- 목적지 MAC 주소가 테이블에 있으면 해당 포트로 전달한다.
- 목적지를 모르는 유니캐스트나 브로드캐스트는 같은 VLAN의 수신 포트 외 다른 포트로 전달한다.

따라서 “스위치는 항상 한 포트로만 전송한다”는 설명은 정확하지 않다.

### 5. 같은 네트워크와 다른 네트워크의 통신

같은 서브넷의 상대에게는 직접 전달하고, 다른 서브넷의 상대에게는 라우터를 통해 전달한다.

```
같은 서브넷
A → 스위치 → B

다른 서브넷
A → 스위치 → 기본 게이트웨이 → 다른 네트워크의 B
```

기본 게이트웨이는 다른 네트워크로 보낼 때 사용하는 기본 출구다. 보통 라우터나 L3 기능을 가진 장비가 담당한다.

A와 B가 서로 다른 네트워크에 있는 경우:

| 구간 | 출발지 IP | 목적지 IP | 출발지 MAC | 목적지 MAC |
| --- | --- | --- | --- | --- |
| A → 라우터 | A | B | A의 MAC | 라우터 수신 인터페이스의 MAC |
| 라우터 → B | A | B | 라우터 송신 인터페이스의 MAC | B의 MAC |
- 일반적인 라우팅에서는 출발지·목적지 IP가 유지된다. NAT를 거치면 달라질 수 있다.
- MAC 주소는 라우터를 통과해 새로운 링크로 전달될 때 바뀐다.
- 같은 링크 안에서 L2 스위치를 통과한다고 MAC 주소가 매번 바뀌는 것은 아니다.
- IPv4의 ARP는 같은 링크에서 다음 전달 대상의 IP에 대응하는 MAC 주소를 알아내는 데 사용한다.
### 6. 포트와 소켓

한 컴퓨터에서는 웹, 메일 등 여러 프로그램이 동시에 통신하므로, 도착한 데이터를 구분할 정보가 필요하다.

| 구분 | 의미 |
| --- | --- |
| 포트 | TCP·UDP에서 통신 종단을 구분하는 번호 |
| 소켓 | 프로그램이 네트워크 통신에 사용하는 종단이자 운영체제 인터페이스 |
| TCP 연결 식별 | 출발지 IP·포트와 목적지 IP·포트의 조합 |

```
클라이언트                     웹 서버
192.0.2.10:50000  ─────────→  198.51.100.20:80
   임시 포트                     서비스 포트
```

- 같은 서버 포트로 여러 클라이언트가 접속해도 출발지 IP·포트가 달라 연결을 구분할 수 있다.
- TCP 포트와 UDP 포트는 별도로 구분된다.
- 하나의 프로그램이 여러 포트를 사용할 수 있으므로 “프로그램 하나 = 포트 하나”는 아니다.
### 7. 캡슐화와 역캡슐화

캡슐화는 상위 계층의 데이터에 현재 계층의 제어 정보를 붙이는 과정이다. 역캡슐화는 이를 확인·제거하며 상위 계층으로 전달하는 과정이다.

```
응용 데이터
    ↓ TCP 헤더 추가
[TCP 헤더 | 데이터]
    ↓ IP 헤더 추가
[IP 헤더 | TCP 헤더 | 데이터]
    ↓ 이더넷 헤더·트레일러 추가
[이더넷 헤더 | IP 헤더 | TCP 헤더 | 데이터 | FCS]
    ↓
비트·신호로 전송
```

| 위치 | 처리 |
| --- | --- |
| 송신 호스트 | 상위 → 하위 계층으로 캡슐화 |
| 수신 호스트 | 하위 → 상위 계층으로 역캡슐화 |
| 라우터 | 수신 링크의 프레임을 벗기고 IP 패킷을 처리한 후, 송신 링크의 프레임으로 다시 감쌈 |
| 일반적인 L2 스위치 | MAC 정보를 보고 프레임을 전달하며, 응용 데이터까지 역캡슐화하지 않음 |

FCS는 프레임의 전송 오류를 검출하는 값이다. 공격자의 의도적인 변조를 막는 암호학적 인증값은 아니다.

### 8. 다중화와 역다중화

다중화는 여러 상위 계층의 데이터를 하나의 하위 계층 프로토콜을 통해 전달하는 것이다.

역다중화는 수신 데이터의 식별 정보를 확인하여 알맞은 상위 프로토콜이나 통신 종단으로 나누는 것이다.

```
송신 측: 다중화                수신 측: 역다중화

웹 ──┐                         ┌── 웹
메일 ─┼→ TCP → IP → 네트워크 → IP → TCP ─┼── 메일
기타 ─┘                         └── 기타
```

수신 측에서 “어디로 넘길지” 판단하는 기준:

| 계층 | 식별 필드 | 구분 대상 |
| --- | --- | --- |
| 이더넷 | EtherType | IPv4, IPv6, ARP 등 |
| IPv4 | Protocol | TCP, UDP, ICMP 등 |
| IPv6 | Next Header | 다음 확장 헤더 또는 상위 프로토콜 |
| TCP·UDP | 포트 번호 등 | 수신 소켓·서비스 |

예를 들어 TCP를 사용하는 웹 요청은 다음 순서로 전달된다.

```
이더넷의 EtherType 확인 → IPv4로 전달
IPv4의 Protocol 확인   → TCP로 전달
TCP의 목적지 포트 확인 → 해당 서버 소켓으로 전달
```

캡슐화는 “제어 정보를 붙여 감싸는 과정”, 다중화는 “여러 통신이 공통 하위 계층을 이용하는 방식”이다.

### 1. TCP/IP 계층별 역할

| 계층 | 핵심 역할 | 대표 프로토콜 |
| --- | --- | --- |
| 응용 | 웹·메일·파일 전송 등 서비스 제공 | HTTP, DNS, SMTP, FTP |
| 전송 | 호스트 내부의 프로세스 간 통신, 포트로 구분 | TCP, UDP |
| 인터넷 | IP 주소를 이용한 패킷 전달과 라우팅 | IP, ICMP, IGMP |
| 네트워크 접근 | 같은 링크에서 프레임 송수신 | Ethernet, ARP |
- IP: 비연결형·최선형 전달. 도착 여부, 순서, 재전송을 보장하지 않음.
- TCP: IP 위에서 순서 제어·재전송 등을 수행하여 신뢰성을 제공.
- UDP: 연결 설정 없이 데이터그램을 전송.

### 2. 패킷 전송 방식

| 방식 | 전달 대상 | 기억할 내용 |
| --- | --- | --- |
| 유니캐스트 | 특정 수신자 한 명 | 1:1 |
| 멀티캐스트 | 특정 그룹의 수신자들 | 1:그룹 |
| 브로드캐스트 | 같은 브로드캐스트 영역의 모든 장치 | 1:전체 |
| 애니캐스트 | 같은 주소를 사용하는 여러 장치 중 하나 | 1:가장 적절한 한 곳 |

애니캐스트의 ‘가까운 장치’는 물리적 거리가 아니라 라우팅 기준으로 선택된 장치를 의미한다.

- IPv6에는 브로드캐스트가 없으며, 필요한 기능을 멀티캐스트로 처리한다.
- 애니캐스트는 IPv4에서도 구현할 수 있다.

### 3. IPv4 주소와 클래스

IPv4 주소는 32비트이며, 네트워크 부분과 호스트 부분으로 나뉜다.

```
192.168.1.10/24

/24 = 앞의 24비트가 네트워크 부분
나머지 8비트 = 호스트 부분
```

| 클래스 | 첫 번째 옥텟 | 기본 프리픽스 | 용도 |
| --- | --- | --- | --- |
| A | 일반 사용 범위 1~126 | /8 | 대규모 네트워크 |
| B | 128~191 | /16 | 중규모 네트워크 |
| C | 192~223 | /24 | 소규모 네트워크 |
| D | 224~239 | 해당 없음 | 멀티캐스트 |
| E | 240~255 | 해당 없음 | 예약 영역 |

클래스는 과거의 주소 분류 방식이다. CIDR에서는 클래스 대신 `/프리픽스 길이`로 네트워크 범위를 판단한다.

사설 주소는 다음 세 범위를 구분해서 기억한다.

| 사설 주소 | 범위 |
| --- | --- |
| 10.0.0.0/8 | 10.0.0.0~10.255.255.255 |
| 172.16.0.0/12 | 172.16.0.0~172.31.255.255 |
| 192.168.0.0/16 | 192.168.0.0~192.168.255.255 |

사설 주소는 내부망에서 사용하며, 공용 인터넷에서 직접 라우팅되지 않는다.

| 특수 주소 | 의미 |
| --- | --- |
| 0.0.0.0 | 아직 주소가 정해지지 않은 상태 등에서 사용 |
| 0.0.0.0/0 | 모든 IPv4 목적지에 대응하는 기본 경로 |
| 127.0.0.0/8 | 자기 자신으로 돌아오는 루프백 영역 |
| 127.0.0.1 | 대표적인 루프백 주소 |
| 255.255.255.255 | 현재 링크에 대한 제한적 브로드캐스트 |

### 4. 서브네팅·슈퍼네팅·CIDR

| 구분 | 의미 | 프리픽스 변화 |
| --- | --- | --- |
| 서브네팅 | 하나의 네트워크를 작은 네트워크 여러 개로 분할 | 길어짐 |
| 슈퍼네팅 | 여러 네트워크를 큰 주소 블록으로 집약 | 짧아짐 |
| CIDR | 클래스에 의존하지 않고 프리픽스 길이로 주소 범위 표현 | `/n` 사용 |

```
/24 → /27 : 네트워크를 더 작게 나눔
/24 → /21 : 더 큰 주소 범위로 묶음
```

계산할 때 필요한 핵심:

```
호스트 비트 수 = 32 - 프리픽스 길이
전체 주소 수 = 2^(호스트 비트 수)

일반적인 IPv4 서브넷의 사용 가능한 호스트 수
= 전체 주소 수 - 2

제외하는 주소:
호스트 부분이 모두 0 → 네트워크 주소
호스트 부분이 모두 1 → 브로드캐스트 주소
```

- `2`는 일반적인 서브넷 기준이며, `/31` 점대점 링크와 `/32`는 별도로 해석한다.

| 프리픽스 | 서브넷 마스크 | 전체 주소 수 | 일반적인 호스트 수 |
| --- | --- | --- | --- |
| /24 | 255.255.255.0 | 256 | 254 |
| /25 | 255.255.255.128 | 128 | 126 |
| /26 | 255.255.255.192 | 64 | 62 |
| /27 | 255.255.255.224 | 32 | 30 |
| /28 | 255.255.255.240 | 16 | 14 |
| /29 | 255.255.255.248 | 8 | 6 |
| /30 | 255.255.255.252 | 4 | 2 |

예시 ① `/20` 네트워크를 동일한 크기 8개로 분할

```
8개 = 2^3
호스트 비트 3개를 네트워크 비트로 전환

새 프리픽스 = /20 + 3 = /23
서브넷 마스크 = 255.255.254.0
```

`28.23.16.0/20`을 나누면:

```
28.23.16.0/23
28.23.18.0/23
28.23.20.0/23
...
28.23.30.0/23
```

예시 ② `/24` 네트워크에서 동일 크기 서브넷을 최소 30개 확보

```
2^4 = 16 → 부족
2^5 = 32 → 충족

새 프리픽스 = /29
서브넷 마스크 = 255.255.255.248
각 서브넷의 사용 가능한 호스트 = 6개
```

주의: ‘서브넷 30개’와 ‘서브넷당 호스트 30개’는 다르다. 호스트 30개가 필요하면 호스트 비트 5개가 필요하므로 `/27`이다.

### 5. IPv4 헤더와 단편화

IPv4 패킷은 `IP 헤더 + 데이터`로 구성된다.

- 헤더 길이: 20~60바이트
- 전체 패킷 길이: 최대 65,535바이트
- IHL은 헤더 길이를 4바이트 단위로 표시 → IHL이 5이면 20바이트

| 주요 필드 | 역할 |
| --- | --- |
| Version | IP 버전, IPv4는 4 |
| IHL | IP 헤더 길이 |
| Total Length | 헤더를 포함한 전체 패킷 길이 |
| TTL | 패킷이 무한히 순환하지 않도록 수명 제한 |
| Protocol | IP 데이터 부분에 담긴 프로토콜 식별 |
| Header Checksum | IPv4 헤더의 오류 검출 |
| Source / Destination Address | 출발지·목적지 IP 주소 |
| Identification | 같은 원본 패킷에서 나온 단편들을 식별 |
| Flags | 단편화 허용 여부와 추가 단편 존재 여부 |
| Fragment Offset | 원본 데이터에서 해당 단편의 위치 |

Protocol 번호와 포트 번호는 구분해야 한다.

```
IP Protocol = 6  → TCP
IP Protocol = 17 → UDP
IP Protocol = 1  → ICMP

TCP 목적지 Port = 80 → 일반적인 HTTP 서비스
```

TTL은 라우터를 지날 때 감소한다. 전달 과정에서 0이 되면 패킷을 폐기하고, 일반적으로 ICMP Time Exceeded로 알린다.

단편화는 IP 패킷이 다음 링크의 MTU보다 클 때 패킷을 나누는 것이다.

| 항목 | 의미 |
| --- | --- |
| DF = 1 | 단편화 금지 |
| MF = 1 | 뒤에 단편이 더 있음 |
| MF = 0 | 마지막 단편 또는 단편화하지 않은 패킷 |
| Fragment Offset | 8바이트 단위의 위치 |
| 재조립 | 최종 목적지에서 수행 |

예를 들어 데이터 4,000바이트, IP 헤더 20바이트, MTU 1,500바이트라면:

| 단편 | 데이터 길이 | IP 헤더 포함 길이 | Offset | MF |
| --- | --- | --- | --- | --- |
| 1 | 1,480 | 1,500 | 0 | 1 |
| 2 | 1,480 | 1,500 | 185 | 1 |
| 3 | 1,040 | 1,060 | 370 | 0 |

```
두 번째 Offset = 1480 / 8 = 185
세 번째 Offset = 2960 / 8 = 370
```

각 단편에는 IP 헤더가 붙으며, 마지막 단편을 제외한 데이터 길이는 8의 배수로 맞춘다.

### 6. IPv4와 IPv6 비교

| 항목 | IPv4 | IPv6 |
| --- | --- | --- |
| 주소 길이 | 32비트 | 128비트 |
| 표기 | 점으로 구분한 10진수 | 콜론으로 구분한 16진수 |
| 기본 헤더 | 20~60바이트 | 40바이트 고정 |
| 헤더 체크섬 | 있음 | 없음 |
| 수명 제한 | TTL | Hop Limit |
| 다음 프로토콜 식별 | Protocol | Next Header |
| 단편화 | 송신 호스트·라우터에서 가능 | 송신 호스트에서만 수행 |
| 브로드캐스트 | 있음 | 없음 |
| 이웃의 링크 계층 주소 확인 | ARP | ICMPv6 기반 NDP |

IPv6 주요 필드:

| 필드 | 핵심 역할 |
| --- | --- |
| Traffic Class | 트래픽의 우선 처리 등에 사용 |
| Flow Label | 같은 흐름의 패킷을 식별 |
| Payload Length | 기본 헤더 40바이트를 제외한 길이 |
| Next Header | 다음 확장 헤더 또는 TCP·UDP 등의 종류 |
| Hop Limit | 전달 가능한 홉 수 제한 |

IPv6의 단편화 정보는 기본 헤더가 아닌 Fragment 확장 헤더에 들어간다.

헷갈리기 쉬운 점:

- IPv6라고 통신이 자동으로 암호화되는 것은 아니다. IPsec은 별도 설정과 사용이 필요하다.
- IPv6 주소 자동 설정이 반드시 MAC 주소를 이용하는 것은 아니다.
- Flow Label이 있다고 대역폭이나 지연 시간이 자동으로 보장되는 것은 아니다.

### 7. IPv4 ↔ IPv6 전환 기술

| 기술 | 동작 방식 | 핵심 |
| --- | --- | --- |
| 듀얼 스택 | IPv4와 IPv6를 모두 지원 | 둘 다 사용 |
| 터널링 | 한 IP 패킷을 다른 IP 패킷 안에 넣어 전달 | 감싸서 통과 |
| 헤더 변환 | IPv4와 IPv6의 헤더·주소 등을 변환 | 서로 번역 |

```
듀얼 스택
장치가 IPv4도 처리하고 IPv6도 처리

터널링
IPv6 패킷 → [IPv4 헤더 | IPv6 패킷] → IPv6 패킷

헤더 변환
IPv6 패킷 → 변환 장치 → IPv4 패킷
```

터널링은 내부 패킷을 유지하며 바깥 헤더를 추가하고, 헤더 변환은 서로 다른 IP 버전 사이의 통신을 위해 패킷 형식을 변환한다.

### 8. ARP·RARP·ICMP·IGMP

| 프로토콜 | 핵심 역할 |
| --- | --- |
| ARP | 같은 링크에서 IPv4 주소에 대응하는 MAC 주소 확인 |
| RARP | MAC 주소를 바탕으로 자신의 IP 주소를 알아내는 과거 방식 |
| ICMP | IP 통신의 오류 보고·진단·제어 |
| IGMP | IPv4 멀티캐스트 그룹 가입 정보를 관리 |

ARP 동작:

```
① ARP 캐시 확인
        ↓ 정보 없음
② 요청을 브로드캐스트
   “이 IP를 가진 장치의 MAC 주소는?”
        ↓
③ 해당 장치가 보통 유니캐스트로 응답
   “내 MAC 주소는 이것”
        ↓
④ ARP 캐시에 저장하고 프레임 전송
```

- 같은 서브넷 목적지 → 목적지의 MAC 주소를 확인.
- 다른 서브넷 목적지 → 다음 홉인 게이트웨이의 MAC 주소를 확인.
- ARP 요청은 라우터를 넘어 원격 목적지까지 전달되지 않는다.
- ARP에는 기본적인 인증 기능이 없어 거짓 매핑을 주입하는 ARP 스푸핑에 취약하다.

```
ARP 캐시: IP 주소 ↔ MAC 주소
스위치 MAC 테이블: MAC 주소 ↔ 스위치 포트
```

### 9. ICMP와 진단 도구

ICMP는 문제를 알려주는 프로토콜이며, 손실된 데이터를 직접 재전송하여 복구하지는 않는다.

| ICMPv4 메시지 | Type | 의미 |
| --- | --- | --- |
| Echo Request | 8 | 응답 요청 |
| Echo Reply | 0 | 요청에 대한 응답 |
| Destination Unreachable | 3 | 목적지·포트 등에 도달 불가 |
| Redirect | 5 | 더 적절한 다음 홉 안내 |
| Time Exceeded | 11 | TTL 만료 또는 단편 재조립 시간 초과 |
- ping: Echo Request / Echo Reply로 응답 여부와 왕복 시간 확인.
- traceroute: TTL을 단계적으로 증가시키고, 중간 라우터의 Time Exceeded 응답으로 경로 확인.
- Source Quench는 과거의 혼잡 통보 메시지로, 폐기된 기능이다.

ICMP는 TCP·UDP를 사용하지 않고 IP 안에 직접 실리므로 포트 번호가 없다.

### 10. TCP와 UDP 비교

| 항목 | TCP | UDP |
| --- | --- | --- |
| 연결 | 연결 지향 | 비연결형 |
| 전달 형태 | 바이트 스트림 | 데이터그램 |
| 신뢰성 | 순서 제어·ACK·재전송 제공 | 자체적으로 제공하지 않음 |
| 메시지 경계 | 보존하지 않음 | 보존 |
| 흐름 제어 | 있음 | 자체 기능 없음 |
| 혼잡 제어 | 있음 | 자체 기능 없음 |
| 헤더 길이 | 20~60바이트 | 8바이트 |
| 특징 | 신뢰성 있는 전송 | 구조가 단순하고 오버헤드가 작음 |
- 흐름 제어: 수신자의 처리 능력을 넘지 않도록 조절.
- 혼잡 제어: 네트워크가 감당할 수 있는 수준으로 전송량 조절.
- UDP를 사용하는 응용 프로그램도 필요하면 재전송·순서 제어를 직접 구현할 수 있다.
- UDP가 모든 상황에서 TCP보다 빠르다고 단정할 수는 없다.

### 11. TCP·UDP 헤더 핵심

UDP 헤더는 네 필드로 구성되며, 각각 16비트이다.

```
출발지 포트 | 목적지 포트 | 길이 | 체크섬
```

UDP의 Length는 `UDP 헤더 8바이트 + 데이터 길이`이다.

TCP는 다음 필드가 중요하다.

| 필드 | 의미 |
| --- | --- |
| Source / Destination Port | 송신·수신 측 통신 종단점 식별 |
| Sequence Number | 해당 세그먼트의 첫 데이터 바이트 번호 |
| Acknowledgment Number | 다음에 받기를 기대하는 바이트 번호 |
| Data Offset | TCP 헤더 길이, 4바이트 단위 |
| Window Size | 수신 측이 받아들일 수 있다고 알리는 데이터 범위 |
| Checksum | 전송 오류 검출 |
| Flags | 연결 설정·종료 등의 제어 정보 |

SEQ·ACK 계산:

```
송신: SEQ = 1001, 데이터 길이 = 100바이트
수신: 1001~1100번 바이트를 연속으로 받음
응답: ACK = 1101

뜻: “1100번까지 받았으니 다음에는 1101번부터 보내.”
```

- TCP 순서 번호는 패킷 개수가 아닌 바이트 기준이다.
- SYN과 FIN은 각각 순서 번호 1개를 소비한다.
- 데이터 없는 순수 ACK는 순서 번호를 소비하지 않는다.
- 체크섬은 전송 오류 검출용이며, 공격자의 위변조를 막는 암호학적 인증 기능은 아니다.

주요 TCP 플래그:

| 플래그 | 의미 |
| --- | --- |
| SYN | 초기 순서 번호 동기화, 연결 설정 |
| ACK | 확인응답 번호가 유효함 |
| FIN | 자신의 데이터 송신 종료 |
| RST | 연결 거부·강제 초기화 |
| PSH | 데이터를 응용 프로그램에 신속하게 전달하도록 요청 |
| URG | 긴급 포인터가 유효함 |

---

### 12. TCP 연결 설정: 3-way handshake

목적은 양쪽의 초기 순서 번호를 교환하고 서로 통신할 준비가 되었는지 확인하는 것이다.

```
클라이언트                              서버
                                      LISTEN
    ───── SYN, SEQ=1000 ──────────────→
SYN-SENT                              SYN-RECEIVED

    ←──── SYN+ACK, SEQ=2000, ACK=1001 ──

    ───── ACK, SEQ=1001, ACK=2001 ────→

ESTABLISHED                           ESTABLISHED
```

| 순서 | 의미 |
| --- | --- |
| SYN | “내 시작 번호는 1000이야. 연결하자.” |
| SYN+ACK | “확인했어. 내 시작 번호는 2000이야.” |
| ACK | “네 시작 번호도 확인했어.” |

TCP 연결 정보를 관리하는 TCB는 이 문맥에서 Transmission Control Block을 뜻한다.

---

### 13. TCP 연결 종료: 일반적인 4-way handshake

TCP는 양방향 통신이므로 각 방향의 송신을 따로 종료한다.

```
먼저 종료하는 A                       상대방 B

    ───────── FIN ──────────────────→
FIN-WAIT-1

    ←──────── ACK ───────────────────
FIN-WAIT-2                            CLOSE-WAIT
                                      남은 송신·종료 처리

    ←──────── FIN ───────────────────
                                      LAST-ACK
    ───────── ACK ──────────────────→
TIME-WAIT                             CLOSED

일정 시간 대기 후 CLOSED
```

| 상태 | 의미 |
| --- | --- |
| FIN-WAIT-1 | 자신의 FIN에 대한 ACK 등을 기다림 |
| FIN-WAIT-2 | 자신의 FIN은 확인받았고, 상대방 FIN을 기다림 |
| CLOSE-WAIT | 상대방 FIN을 받았고, 자신의 응용 프로그램이 종료하기를 기다림 |
| LAST-ACK | 자신의 FIN에 대한 마지막 ACK를 기다림 |
| TIME-WAIT | 마지막 ACK 재전송에 대비하고 이전 연결의 지연 패킷이 사라지기를 기다림 |
- TIME-WAIT의 대기 시간은 원칙적으로 2MSL이다.
- CLOSE-WAIT가 오래 유지되면 응용 프로그램이 소켓을 제대로 닫지 않는지 확인한다.
- FIN과 ACK가 함께 전송될 수도 있어 실제 패킷이 항상 네 개로 나뉘는 것은 아니다.

포트 번호는 16비트이며 범위는 `0~65535`이다.

| 구분 | 범위 |

| Well-known | 0~1023 |

| --- | --- | --- | --- |

| FTP 제어 | 21 | TCP | 명령·응답 |
| SSH | 22 | TCP | 보안 원격 접속, SFTP 등 |
| Telnet | 23 | TCP | 평문 원격 접속 |
| SMTP | 25 | TCP | 메일 서버 간 전송 |
| DNS | 53 | UDP·TCP | 이름 해석 |
| DHCP | 67 / 68 | UDP | 서버 / 클라이언트 |
| TFTP | 69 | UDP | 초기 파일 전송 요청 |
| HTTP | 80 | TCP | 웹 서비스 |
| POP3 | 110 | TCP | 메일 수신 |

포트는 서비스의 대표적인 약속이다. 포트 번호만 보고 실제 응용 프로토콜이나 안전성을 확정할 수는 없다.

### 1. 라우팅의 개념

라우팅은 패킷이 목적지까지 도달할 경로를 결정하는 과정이다. 라우터는 목적지 IP 주소를 확인하고 라우팅 테이블에 따라 다음 장비로 전달한다.

| 용어 | 의미 |
| --- | --- |
| 라우팅 | 목적지까지의 경로를 결정하고 경로 정보를 관리 |
| 포워딩 | 결정된 경로에 따라 실제 패킷을 다음 장비로 전달 |
| 라우팅 테이블 | 목적지 네트워크, 다음 홉, 출력 인터페이스 등의 경로 정보 |
| 메트릭(Metric) | 경로를 비교하는 기준값. 홉 수, 비용, 대역폭·지연 등을 활용 |
| 수렴(Convergence) | 네트워크 변화가 반영되어 라우터들의 경로 정보가 안정된 상태에 도달하는 것 |

목적지에 일치하는 경로가 여러 개면 가장 구체적인 경로, 즉 프리픽스가 가장 긴 경로를 우선한다.

```
목적지: 192.168.1.10

192.168.0.0/16
192.168.1.0/24   → 더 구체적이므로 선택
0.0.0.0/0       → 다른 경로가 없을 때 사용하는 기본 경로
```

### 2. 정적 라우팅과 동적 라우팅

| 구분 | 정적 라우팅 | 동적 라우팅 |
| --- | --- | --- |
| 설정 방식 | 관리자가 직접 경로 설정 | 라우팅 프로토콜로 경로 정보 교환 |
| 장애·변화 대응 | 일반적으로 관리자가 수정 | 변화에 따라 자동으로 경로 재계산 |
| 자원 사용 | 상대적으로 적음 | 정보 교환과 계산에 자원 필요 |
| 적합한 환경 | 작고 변화가 적은 네트워크 | 크고 변화가 많은 네트워크 |
| 주요 한계 | 규모가 커지면 관리 어려움 | 설정이 복잡하고 수렴 시간이 필요 |
### 3. AS와 IGP·EGP

AS(Autonomous System)는 하나의 관리 체계와 공통된 라우팅 정책으로 운영되는 네트워크 집합이다.

| 구분 | 역할 | 대표 프로토콜 |
| --- | --- | --- |
| IGP | AS 내부의 경로 정보 교환 | RIP, OSPF, EIGRP |
| EGP | AS 사이의 경로 정보 교환 | BGP |

```
[ AS 1 내부 ] ─────── [ AS 2 내부 ]
  RIP·OSPF     BGP      RIP·OSPF
    IGP       EGP        IGP
```

BGP는 AS 간 연결뿐 아니라, AS 내부에서 외부 경로 정보를 공유하는 데에도 사용된다.

### 4. 거리벡터와 링크상태 비교

거리벡터는 이웃이 알려준 목적지까지의 거리를 바탕으로 경로를 정한다. 링크상태는 네트워크 연결 지도를 공유하고 각 라우터가 직접 경로를 계산한다.

| 구분 | 거리벡터 | 링크상태 |
| --- | --- | --- |
| 기본 관점 | “이웃을 거치면 목적지까지 얼마나 걸리는가?” | “네트워크가 어떻게 연결되어 있는가?” |
| 교환 정보 | 목적지까지의 거리와 경로 정보 | 자신의 링크 상태와 비용 |
| 정보 전달 | 인접 라우터와 교환 | 링크 상태 정보를 영역 내에 전파 |
| 경로 계산 | 이웃이 알려준 비용에 자신의 비용을 더함 | 토폴로지 정보를 바탕으로 최단 경로 계산 |
| 대표 알고리즘 | Bellman-Ford | Dijkstra |
| 대표 프로토콜 | RIP | OSPF |
| 특징 | 구조가 단순하지만 루프·느린 수렴 문제가 발생할 수 있음 | 계산·메모리 부담이 있지만 변화에 비교적 빠르게 대응 |

예를 들어 A→B 비용이 2이고, B가 목적지까지의 비용을 5라고 알려주면 A는 B를 거치는 비용을 7로 계산한다.

주의할 점:

- 거리벡터가 모두 브로드캐스트를 쓰는 것은 아니다. RIPv2는 멀티캐스트를 사용한다.
- OSPF는 변경 시 정보를 전파하지만, 이웃 확인과 주기적인 정보 갱신도 수행한다.
- OSPF의 상세한 링크 상태 정보 공유 범위는 기본적으로 같은 영역(Area)이다.
### 5. 주요 라우팅 프로토콜

| 프로토콜 | 방식 | 경로 선택 기준·알고리즘 | 핵심 특징 |
| --- | --- | --- | --- |
| RIPv1 | 거리벡터 | 홉 수, Bellman-Ford | 서브넷 마스크를 전달하지 않는 클래스 기반 방식 |
| RIPv2 | 거리벡터 | 홉 수, Bellman-Ford | 서브넷 마스크 전달, CIDR·VLSM 및 인증 지원 |
| IGRP | 거리벡터 | 복합 메트릭 | Cisco가 개발한 구형 프로토콜 |
| EIGRP | 고급 거리벡터 | DUAL, 기본적으로 대역폭·지연 활용 | 빠른 수렴, CIDR·VLSM 지원 |
| OSPF | 링크상태 | 비용(Cost), Dijkstra | 영역을 나눠 관리하며 백본은 Area 0 |
| BGP | 경로벡터 | 경로 속성과 정책 | AS 경로 정보를 이용하며 AS 간 라우팅에 사용 |

RIP에서 기억할 내용:

- 최대 유효 홉 수는 15이며, 16은 도달 불가를 의미한다.
- 홉 수만 비교하므로 대역폭이 좋은 경로를 반드시 선택하지는 않는다.
- RIPv1은 브로드캐스트, RIPv2는 일반적으로 224.0.0.9 멀티캐스트를 사용한다.
- 둘 다 UDP 520번을 사용한다.

OSPF와 BGP에서 기억할 내용:

- OSPF: 같은 영역의 연결 정보를 공유하고 각 라우터가 최단 경로를 계산한다.
- OSPF: TCP·UDP 포트 대신 IP 프로토콜 번호 89를 사용한다.
- BGP: TCP 179번을 사용한다.
- BGP: 단순 최단 거리보다 운영 정책과 경로 속성을 반영한다.
- AS_PATH: 지나온 AS 목록으로, 자신의 AS가 포함된 경로를 확인해 루프를 방지한다.
### 6. 라우터 ACL

ACL(Access Control List)은 패킷의 주소·프로토콜·포트 등을 검사해 통과 또는 차단하는 규칙 목록이다.

| 구분 | 표준 ACL | 확장 ACL |
| --- | --- | --- |
| 주요 검사 항목 | 출발지 IP | 출발지·목적지 IP, 프로토콜, 포트 등 |
| 제어 수준 | 단순한 주소 기반 제어 | 서비스 단위의 세밀한 제어 |
| 예시 | 특정 출발지 차단 | 특정 출발지의 SSH 접속만 차단 |

ACL의 핵심 동작:

- 위에서 아래로 검사하고, 처음 일치한 규칙을 적용한다.
- 일반적인 Cisco IP ACL에는 마지막에 암묵적 전체 거부가 있다.
- 규칙을 작성한 뒤 인터페이스와 적용 방향을 지정해야 한다.
- `in`은 해당 인터페이스로 들어오는 패킷, `out`은 나가는 패킷에 적용한다.

와일드카드 마스크:

| 비트 | 의미 |
| --- | --- |
| 0 | 해당 주소 비트를 비교 |
| 1 | 해당 주소 비트를 무시 |

```
192.168.1.0 0.0.0.255
→ 앞의 192.168.1은 일치해야 하고 마지막 부분은 무관
→ 192.168.1.0/24 범위

host 192.168.1.10
→ 해당 IP 하나

any
→ 모든 IP
```

예시:

```
access-list 101 deny tcp 192.168.1.0 0.0.0.255 host 10.0.0.10 eq 22
access-list 101 permit ip any any
```

- 첫 규칙: 192.168.1.0/24에서 10.0.0.10으로 향하는 SSH(TCP 22) 접속 차단.
- 둘째 규칙: 위 조건에 해당하지 않는 나머지 IP 통신 허용.
- 둘째 규칙이 없으면 나머지 통신도 암묵적 거부에 의해 차단된다.
### 7. 라우터 보안 관련 개념

| 개념 | 핵심 내용 |
| --- | --- |
| Ingress 필터링 | 들어오는 트래픽을 검사해 위조되거나 허용되지 않은 출발지 주소 등을 차단 |
| Egress 필터링 | 나가는 트래픽을 검사해 내부에서 발생하는 주소 위조·불필요한 통신 등을 차단 |
| uRPF | 출발지 IP로 돌아가는 경로를 확인하여 출발지 주소의 타당성을 검사 |
| 블랙홀 라우팅 | 특정 목적지 트래픽을 Null 인터페이스 등으로 보내 폐기 |
| Source Routing | 송신자가 패킷이 거칠 경로를 지정하는 방식 |

uRPF의 엄격 모드는 출발지로 돌아가는 최적 경로의 인터페이스와 실제 수신 인터페이스가 일치하는지 확인한다. 따라서 왕복 경로가 다른 비대칭 라우팅에서는 정상 패킷도 차단할 수 있다.

### SECTION 22. 네트워크 장비의 이해


**연결 기출 Q300–Q306**

### 1. 네트워크 장비와 동작 계층

장비는 무엇을 보고 데이터를 전달하는지로 구분하면 된다.

| 계층 | 장비 | 판단 기준과 역할 |
| --- | --- | --- |
| L1 물리 | 리피터 | 약해진 신호를 재생하여 전송 거리 확장 |
| L1 물리 | 허브 | 들어온 신호를 수신 포트 외의 모든 포트로 전달 |
| L2 데이터링크 | 브리지, L2 스위치 | MAC 주소를 보고 같은 LAN 안에서 프레임 전달 |
| L3 네트워크 | 라우터, L3 스위치 | IP 주소를 보고 서로 다른 네트워크 사이에서 패킷 전달 |
| L4 전송 | L4 스위치 | IP 주소·포트 번호 등을 기준으로 서버 부하 분산 |
| L7 응용 | L7 스위치 | URL·HTTP 헤더 등 응용 내용을 기준으로 서버 부하 분산 |
| 여러 계층 | 게이트웨이 | 서로 다른 통신 방식이나 프로토콜을 연결·변환 |
- 허브: 목적지를 구분하지 않고 모두에게 전달.
- L2 스위치: 목적지 MAC 주소에 해당하는 포트로 전달.
- 라우터: 목적지 IP 주소에 맞는 다음 경로로 전달.
- 기본 게이트웨이: 다른 네트워크로 나갈 때 사용하는 출구로, 보통 라우터가 담당.
### 2. 브리지와 라우터 비교

| 구분 | 브리지 | 라우터 |
| --- | --- | --- |
| 동작 계층 | L2 | L3 |
| 판단 주소 | MAC 주소 | IP 주소 |
| 참조 정보 | MAC 주소 테이블 | 라우팅 테이블 |
| 주요 역할 | LAN 구간을 연결 | 서로 다른 네트워크를 연결 |
| 브로드캐스트 | 같은 VLAN 안에서 전달 | 기본적으로 다른 네트워크로 전달하지 않음 |
| 목적지 정보가 없을 때 | 수신 포트 외 같은 VLAN의 포트로 플러딩 | 기본 경로까지 포함해 일치하는 경로가 없으면 폐기 |

브리지는 충돌 영역을 나누지만, 브로드캐스트 영역은 나누지 않는다. 브로드캐스트 영역은 라우터 또는 VLAN으로 구분한다.

### 3. 스위치의 동작과 전송 방식

스위치는 출발지 MAC 주소로 학습하고, 목적지 MAC 주소로 전달한다.

```
프레임 수신
    ↓
출발지 MAC 주소와 들어온 포트를 테이블에 기록
    ↓
목적지 MAC 주소 조회
    ├─ 알고 있음 → 해당 포트로 전달
    └─ 모름 → 같은 VLAN의 다른 포트로 플러딩
```

브로드캐스트 프레임도 같은 VLAN의 다른 포트로 전달한다.

| 전송 방식 | 동작 | 특징 |
| --- | --- | --- |
| Cut-through | 목적지 MAC 주소를 확인하면 바로 전달 시작 | 지연이 작지만 오류 프레임도 전달 가능 |
| Store-and-forward | 전체 프레임을 받은 뒤 FCS로 오류 검사 후 전달 | 오류 프레임을 걸러낼 수 있음 |
| Fragment-free | 처음 64바이트를 받은 뒤 전달 시작 | 짧은 충돌 조각을 걸러내는 절충 방식 |

스위치가 있다고 스니핑이 완전히 차단되는 것은 아니다. ARP 스푸핑 등의 공격에는 별도 대응이 필요하다.

### 4. VLAN의 개념과 통신

VLAN은 물리적인 스위치 구성과 관계없이 LAN을 논리적으로 나누는 기술이다. 각 VLAN은 별도의 브로드캐스트 영역이 된다.

```
하나의 물리적 스위치
    ├─ VLAN 10: 인사팀 PC들
    └─ VLAN 20: 회계팀 PC들

인사팀에서 보낸 브로드캐스트 → VLAN 10 안에서만 전달
회계팀과 통신하려면 → 라우터 또는 L3 스위치 필요
```

- 하나의 스위치에 여러 VLAN을 구성할 수 있다.
- 하나의 VLAN을 여러 스위치에 걸쳐 구성할 수도 있다.
- 같은 VLAN 내부 통신은 L2 스위칭으로 처리한다.
- 서로 다른 VLAN 간 통신은 L3 라우팅이 필요하다.
- VLAN 간 통신을 제한하려면 ACL이나 방화벽 정책을 적용한다.

| 포트 종류 | 역할 |
| --- | --- |
| Access 포트 | 일반적으로 하나의 VLAN에 속하며 PC 같은 단말 연결 |
| Trunk 포트 | 여러 VLAN의 트래픽을 함께 운반하며 스위치 간 연결 등에 사용 |

IEEE 802.1Q는 프레임에 VLAN 식별 정보를 붙이는 태깅 방식이다. 트렁크에서 여러 VLAN의 트래픽을 구분하는 데 사용한다.

### 5. VLAN 분류 기준

| 종류 | VLAN을 나누는 기준 | 핵심 |
| --- | --- | --- |
| 포트 기반 | 스위치의 물리적 포트 | 가장 일반적인 방식. 연결한 포트에 따라 소속 결정 |
| MAC 기반 | 단말의 MAC 주소 | 포트가 바뀌어도 MAC을 기준으로 소속 유지 가능 |
| 네트워크 주소 기반 | IP 주소·서브넷 | 네트워크 주소에 따라 소속 결정 |
| 프로토콜 기반 | 사용하는 통신 프로토콜 | 프로토콜 종류에 따라 소속 결정 |

포트 기반 VLAN에서는 PC를 다른 포트로 옮기면 소속 VLAN이 달라질 수 있다. 따라서 “자리를 옮겨도 VLAN이 자동 유지된다”는 설명은 모든 방식에 적용되지 않는다.

### 6. 헷갈리기 쉬운 구분

| 개념 | 의미 | 구분 기준 |
| --- | --- | --- |
| 충돌 도메인 | 신호 충돌이 영향을 미치는 범위 | 허브는 공유, 스위치는 포트별 분리 |
| 브로드캐스트 도메인 | 브로드캐스트가 전달되는 범위 | VLAN별 분리, 라우터가 경계 역할 |
- 스위치 포트가 다르다고 서로 다른 VLAN인 것은 아니다.
- 같은 스위치에 연결되어 있어도 VLAN이 다르면 별도 네트워크로 구분할 수 있다.
- VLAN은 논리적 망 분리 기술이며, 통신 내용을 암호화하는 기술은 아니다.

### 1. 무선 LAN 기본 개념과 표준

무선 LAN은 전파로 데이터를 전달하는 네트워크이며, 대표적인 표준은 IEEE 802.11이다.

- AP: 무선 단말을 네트워크에 연결하는 접속 장치.
- STA: 노트북·스마트폰 같은 무선 단말.
- SSID: 무선 네트워크의 이름. 비밀번호나 인증 수단은 아니다.

| 표준 | 주파수 대역 | 최대 이론 속도 | 핵심 특징 |
| --- | --- | --- | --- |
| 802.11b | 2.4GHz | 11Mbps | 초기 무선 LAN |
| 802.11a | 5GHz | 54Mbps | b와 주파수 대역이 다름 |
| 802.11g | 2.4GHz | 54Mbps | b와 호환 |
| 802.11n | 2.4GHz·5GHz | 600Mbps | 여러 안테나를 사용하는 MIMO |
| 802.11i | 특정 대역·속도를 정의하지 않음 | 해당 없음 | 무선 LAN 보안 강화, WPA2의 기반 |

교재의 802.11i를 ‘2.4GHz·11Mbps’로 외우면 안 된다. 전송속도 표준이 아니라 보안 표준이다.

무선 LAN의 매체 접근 방식은 CSMA/CA다.

| 구분 | 의미 | 동작 |
| --- | --- | --- |
| CSMA/CD | 충돌 감지 | 전송 중 충돌을 감지하고 재전송 |
| CSMA/CA | 충돌 회피 | 전송 전 대기·임의 지연 등으로 충돌 가능성을 줄임 |

CSMA/CD는 전통적인 반이중 이더넷의 방식이며, 전이중 스위치 이더넷에서는 사용하지 않는다.

### 2. 무선 LAN의 주요 보안 위협

무선은 전파가 건물 밖까지 전달될 수 있어, 물리적으로 내부에 들어오지 않아도 통신에 접근할 수 있다는 점이 핵심이다.

| 위협 | 개념 |
| --- | --- |
| 도청 | 전파를 수신하여 통신 내용을 수집 |
| 비인가 접속 | 인증이 없거나 취약한 무선망에 무단 접속 |
| MAC 스푸핑 | 허용된 단말의 MAC 주소를 사칭 |
| Rogue AP | 관리자의 승인 없이 설치된 AP |
| Evil Twin | 정상 AP와 비슷한 이름 등으로 위장해 접속을 유도하는 가짜 AP |
| DoS·전파 방해 | 대량 요청이나 방해 전파로 정상 통신을 방해 |
| 물리적 공격 | AP 도난·파손·초기화·케이블 분리 |

주의할 구분:

- SSID 숨김: 네트워크 이름을 숨기는 보조 조치일 뿐, 인증을 대신하지 못함.
- MAC 필터링: MAC 주소를 알아내고 위조할 수 있으므로 단독 방어에 한계가 있음.
- Rogue AP는 직원이 임의로 설치한 AP도 포함하며, 모두 Evil Twin인 것은 아님.

### 3. WEP·WPA·WPA2 비교

인증은 ‘누가 접속하는가’를 확인하고, 암호화는 ‘전송 내용을 읽지 못하게’ 보호한다.

| 구분 | 대표 암호화 방식 | 무결성 검사 | 핵심 |
| --- | --- | --- | --- |
| WEP | RC4 | CRC-32 기반 ICV | 짧은 IV와 키 재사용 등의 구조적 취약점 |
| WPA | TKIP·RC4 | MIC | 기존 WEP 장비의 보안을 개선한 과도기 방식 |
| WPA2 | AES 기반 CCMP | CBC-MAC | 802.11i 기반 보안 방식 |
- WEP: 24비트 IV를 사용하며, IV 반복 등으로 키 추정 공격에 취약하다.
- TKIP: 패킷별 키 혼합, 무결성 검사, 재전송 공격 방어 등을 추가했지만 RC4 기반이다.
- CCMP: AES를 이용해 기밀성과 무결성을 함께 제공한다.

CCMP의 역할은 다음처럼 구분하면 된다.

```
AES-CTR → 데이터 암호화 → 기밀성
CBC-MAC → 변조 여부 검사 → 무결성·데이터 인증
```

WEP의 CRC-32는 오류 검출용이므로, 공격자의 의도적인 변조를 막는 암호학적 MAC과 다르다.

### 4. Personal·Enterprise와 802.1X

WPA·WPA2의 Personal과 Enterprise는 주로 인증 방식의 차이다.

| 구분 | Personal | Enterprise |
| --- | --- | --- |
| 인증 방식 | PSK, 사전 공유키 | 802.1X·EAP |
| 사용자 구분 | 여러 사용자가 같은 비밀번호를 공유할 수 있음 | 사용자·기기별 인증 가능 |
| 인증 서버 | 별도 서버 없이 가능 | 일반적으로 RADIUS 서버 사용 |
| 관리 특징 | 설정이 간단함 | 계정별 접근 허용·철회가 용이 |

802.1X는 인증 결과에 따라 네트워크 포트의 접근을 통제하는 방식이다. 유선과 무선 모두에 적용할 수 있다.

```
단말                 AP·스위치                  인증 서버
Supplicant   ↔   Authenticator       ↔       RADIUS
인증 요청            인증 중계·접근 통제         인증 판단
```

| 구성요소 | 역할 |
| --- | --- |
| Supplicant | 인증을 요청하는 사용자 단말 |
| Authenticator | 인증 메시지를 중계하고 네트워크 접근을 통제 |
| Authentication Server | 자격정보를 확인하고 인증 결과를 반환 |
- EAP: 다양한 인증 방법을 담을 수 있는 인증 프레임워크.
- RADIUS: 중앙에서 인증·인가·사용 기록 관리를 지원하는 프로토콜.
- 인증 성공 후 일반 데이터 통신을 허용하는 것이 기본 흐름이다.

AAA도 함께 구분한다.

| 요소 | 의미 |
| --- | --- |
| Authentication | 누구인지 확인하는 인증 |
| Authorization | 무엇을 할 수 있는지 결정하는 인가 |
| Accounting | 접속 시간·사용 내역 등의 기록 |

### 6. WAP와 WTLS

WAP는 초기 모바일 기기에서 웹과 같은 정보 서비스를 이용하도록 만든 프로토콜 체계다. Wi-Fi 보안 규격인 WPA와 이름을 혼동하지 않도록 한다.

| 계층 | 프로토콜 | 역할 |
| --- | --- | --- |
| 응용 | WAE | 무선 응용 실행 환경 |
| 세션 | WSP | 세션 관리 |
| 트랜잭션 | WTP | 요청·응답 트랜잭션 처리 |
| 보안 | WTLS | 무선 구간의 보안 |
| 전송 | WDP | 하위 통신망에 독립적인 데이터그램 전달 |

전통적인 WAP 게이트웨이 구조:

```
모바일 단말 ── WTLS ── WAP 게이트웨이 ── TLS ── 웹 서버
```

게이트웨이에서 WTLS와 TLS를 변환하면서 데이터가 복호화될 수 있다. 따라서 두 구간이 암호화되어 있어도 단말부터 서버까지 하나의 암호화 연결로 보호되는 것은 아니다. 이를 WAP Gap이라고 한다.

### 8. BYOD와 보안 관리 기술

BYOD는 개인 소유 스마트폰·노트북 등을 회사 업무에 사용하는 방식이다.

개인 기기에 회사 자료가 저장되므로, 업무정보 보호와 개인 프라이버시를 함께 고려해야 한다.

| 기술 | 관리 대상 | 핵심 기능 |
| --- | --- | --- |
| MDM | 기기 | 화면 잠금, 암호화 정책, 원격 잠금·삭제 등 |
| MAM | 업무용 앱 | 업무 앱의 배포·설정·데이터 사용 통제 |
| 컨테이너화 | 기기 내 업무 영역 | 개인 데이터와 업무 데이터를 논리적으로 분리 |
| 모바일 가상화 | 별도 실행 환경·OS | 개인용과 업무용 환경을 분리 |
| NAC | 네트워크 접속 | 사용자·기기의 보안 상태를 확인하여 접속 허용·차단 |

```
MDM → 기기 관리
MAM → 앱 관리
컨테이너화 → 업무·개인 영역 분리
NAC → 네트워크 진입 통제
```

예를 들어 개인 스마트폰에서 회사 메일을 사용한다면, 업무 영역의 자료 복사를 제한하고 퇴사 시 업무 데이터만 삭제하는 방식으로 회사 정보와 개인 정보를 함께 보호할 수 있다.

### 2. SNMP — 네트워크 장비를 감시·관리하는 프로토콜

SNMP(Simple Network Management Protocol)는 관리 시스템이 라우터·스위치·서버 등의 상태를 조회하거나 설정을 변경하는 데 사용하는 프로토콜이다.

| 구성요소 | 역할 | 쉽게 이해하기 |
| --- | --- | --- |
| Manager | 관리 정보를 요청하고 장비를 감시·제어 | 중앙 관리실 |
| Agent | 관리 대상 장비에서 요청을 처리하고 상태를 보고 | 장비에 설치된 관리 담당 프로그램 |
| MIB | 관리할 객체의 이름·자료형·의미 등을 정의한 정보 체계 | 관리 항목 목록 |
| SMI | 관리 객체를 정의하고 표현하는 규칙 | 관리 항목을 작성하는 문법 |
| OID | 각 관리 객체를 구분하는 계층형 식별자 | 관리 항목의 고유 번호 |

예를 들어 ‘스위치 포트의 송신 바이트 수’가 관리 객체이고, Manager는 해당 OID를 지정하여 Agent에 값을 요청한다.

SMI는 정의 규칙, MIB는 그 규칙으로 정의한 관리 항목, SNMP는 해당 값을 주고받는 통신 수단이다.

| 메시지 | 방향 | 기능 |
| --- | --- | --- |
| Get | Manager → Agent | 특정 항목의 값 조회 |
| GetNext | Manager → Agent | 다음 관리 항목 조회 |
| GetBulk | Manager → Agent | 여러 항목을 효율적으로 조회 |
| Set | Manager → Agent | 변경 가능한 항목의 값 설정 |
| Response | Agent → Manager | 요청에 대한 결과 응답 |
| Trap | Agent → Manager | 요청 없이 장애·이벤트를 통보 |

```
일반적인 상태 조회
Manager ── Get 요청 ──→ Agent
Manager ←── Response ── Agent

장애·이벤트 발생
Manager ←── Trap ────── Agent
          사전 요청 없음
```

- UDP 161: Agent가 조회·설정 요청을 받는 포트.
- UDP 162: Manager가 Trap 등의 알림을 받는 포트.
- Trap은 별도의 응답 확인이 없다. 응답 확인이 필요한 알림에는 Inform을 사용한다.

---

### 3. SSH — 암호화된 원격 접속

SSH(Secure Shell)는 다른 컴퓨터에 안전하게 접속하여 명령을 실행하거나 파일을 전송하는 프로토콜이다. 기본 포트는 TCP 22이다.

| 기능 | 설명 |
| --- | --- |
| 원격 접속 | 원격 서버에 로그인하여 명령 실행 |
| 인증 | 서버의 신원과 접속 사용자의 신원 확인 |
| 기밀성 | 통신 내용을 암호화하여 도청 방지 |
| 무결성 | 전송 중 데이터 변조 탐지 |
| 파일 전송 | SFTP·SCP를 통한 안전한 파일 전송 |
| 포트 포워딩 | 다른 서비스의 트래픽을 SSH 연결로 전달 |
| 다중화 | 하나의 SSH 연결에서 여러 논리적 채널 사용 |

Telnet·rlogin·rsh처럼 평문 통신에 의존하는 원격 접속 방식의 문제를 해결한다.

---

### 4. SSH의 3가지 구성 프로토콜

| 구성 | 핵심 역할 | 기억할 내용 |
| --- | --- | --- |
| SSH-TRANS | 안전한 통신 기반 구성 | 서버 인증, 키 교환, 암호화, 무결성 보호 |
| SSH-AUTH | 접속 사용자 인증 | 비밀번호·공개키 등의 방식으로 사용자 확인 |
| SSH-CONN | 여러 논리적 채널 관리 | 원격 셸, 파일 전송, 포트 포워딩 |

```
TCP 연결
   ↓
SSH-TRANS: 서버 확인 + 키 교환 + 암호화 통신 준비
   ↓
SSH-AUTH: 접속 사용자 인증
   ↓
SSH-CONN: 필요한 채널 생성
   ├─ 원격 명령 실행
   ├─ 파일 전송
   └─ 포트 포워딩
```

구분할 점:

- 서버 인증: ‘내가 접속한 서버가 진짜인가?’ → SSH-TRANS
- 사용자 인증: ‘접속한 사용자가 허가된 사람인가?’ → SSH-AUTH
- SSH의 ‘전송 계층 프로토콜’이라는 이름을 TCP와 같은 OSI 4계층으로 혼동하지 않는다. SSH는 TCP 위에서 동작한다.

---

### 5. 헷갈리는 개념 비교

| 비교 | 차이 |
| --- | --- |
| SNMP / SSH | SNMP는 장비 상태 조회·관리, SSH는 안전한 원격 접속·명령 실행 |
| SFTP / FTPS | SFTP는 SSH 기반 파일 전송, FTPS는 FTP에 TLS를 적용한 방식 |
| SFTP / SCP | 둘 다 SSH를 이용하며, SFTP는 파일 관리 기능을 제공하고 SCP는 파일 복사에 초점 |
| 포트 포워딩 / 다중화 | 포트 포워딩은 다른 통신을 SSH로 전달, 다중화는 하나의 SSH 연결을 여러 채널로 나눠 사용 |

SSH 포트 포워딩의 암호화 범위는 SSH 클라이언트와 SSH 서버 사이이다. SSH 서버에서 최종 목적지까지의 구간은 해당 서비스가 별도로 암호화하지 않으면 보호되지 않는다.

### 2. ping — “상대방에게 도달할 수 있는가?”

ICMP 요청을 보내고 응답을 받아 네트워크 연결 상태를 확인한다.

```
내 컴퓨터 ── Echo Request ──→ 대상
내 컴퓨터 ←── Echo Reply ─── 대상
           왕복 시간 = RTT
```

| ICMPv4 메시지 | Type | 의미 |
| --- | --- | --- |
| Echo Request | 8 | 응답 요청 |
| Echo Reply | 0 | 요청에 대한 응답 |
- RTT: 요청을 보낸 뒤 응답을 받을 때까지 걸린 왕복 시간.
- 손실률: 보낸 요청 중 응답을 받지 못한 비율.
- TTL: 라우터를 통과할 때 감소하며, 패킷이 무한히 순환하는 것을 방지한다.

주의할 점:

- ping 응답이 없어도 상대 시스템이 꺼졌다고 단정할 수 없다. 방화벽에서 ICMP를 차단했을 수도 있다.
- ping 성공은 웹·메일 같은 개별 서비스의 정상 동작까지 보장하지 않는다.
- RTT가 짧다고 물리적으로 더 가까운 것은 아니다.
- 초기 TTL은 운영체제와 설정에 따라 다르므로, TTL만으로 OS를 확정할 수 없다.

---

### 3. traceroute / tracert — “어떤 경로로 가는가?”

TTL을 1부터 차례로 증가시키며 패킷을 보내 중간 라우터를 알아낸다.

```
출발지 ── 라우터 A ── 라우터 B ── 목적지

TTL 1 → A에서 만료 → A가 ICMP Time Exceeded 응답
TTL 2 → B에서 만료 → B가 ICMP Time Exceeded 응답
TTL 3 → 목적지 도착 → 목적지의 응답 확인
```

| 구분 | 일반적인 UNIX/Linux traceroute | Windows tracert |
| --- | --- | --- |
| 보내는 탐색 패킷 | UDP | ICMP Echo Request |
| 중간 라우터의 응답 | ICMP Time Exceeded | ICMP Time Exceeded |
| 목적지 도착 시 응답 | ICMP Port Unreachable | ICMP Echo Reply |

traceroute는 구현과 옵션에 따라 ICMP나 TCP 방식도 사용할 수 있다.

- 출력 시간은 출발지에서 해당 홉까지의 왕복 시간이다. 인접 라우터 사이의 시간은 아니다.
- `*`는 제한 시간 내 응답을 받지 못했다는 뜻이다. 해당 라우터의 장애를 확정하는 표시는 아니다.

암기: ping은 도달 여부, traceroute는 도달 경로.

---

### 4. netstat — “누구와 어떤 포트로 통신 중인가?”

현재 시스템의 소켓과 연결 상태, 라우팅 정보, 프로토콜 통계를 확인한다.

| 주요 출력 항목 | 의미 |
| --- | --- |
| Proto | TCP·UDP 등 사용 프로토콜 |
| Local Address | 내 IP 주소와 포트 |
| Foreign Address | 상대 IP 주소와 포트 |
| State | TCP 연결 상태 |

| TCP 상태 | 의미 |
| --- | --- |
| LISTEN / LISTENING | 접속 요청을 기다리는 상태 |
| SYN_SENT | SYN을 보내고 응답을 기다리는 상태 |
| SYN_RECEIVED | SYN을 받아 SYN+ACK을 보내고 최종 ACK 대기 |
| ESTABLISHED | 연결이 성립된 상태 |
| CLOSE_WAIT | 상대의 종료 요청을 받고, 내 프로그램의 연결 종료를 기다림 |
| TIME_WAIT | 마지막 ACK 재전송과 지연 패킷 처리를 위해 일정 시간 대기 |

주요 옵션은 운영체제에 따라 일부 다르다.

| 옵션 | 의미 |
| --- | --- |
| `-a` | 연결 및 대기 소켓 표시 |
| `-n` | 주소와 포트를 이름 대신 숫자로 표시 |
| `-r` | 라우팅 테이블 표시 |
| `-s` | 프로토콜별 통계 표시 |
| `-i` | 인터페이스 정보 표시 — UNIX/Linux 계열 |
| `-o` | 연결에 관련된 PID 표시 — Windows |

예: Windows의 `netstat -ano`는 연결·대기 포트와 주소를 숫자로 표시하고 PID까지 보여준다.

### 5. route — “목적지로 보낼 다음 경로는 어디인가?”

라우팅 테이블을 조회하거나 경로를 추가·삭제하는 도구다.

| 라우팅 정보 | 의미 |
| --- | --- |
| 목적지 네트워크 | 패킷을 보낼 대상 네트워크 |
| 서브넷 마스크 / 프리픽스 | 목적지 네트워크의 범위 |
| 게이트웨이 | 다음으로 전달할 라우터 |
| 인터페이스 | 패킷을 내보낼 내 네트워크 인터페이스 |
| 메트릭 | 경로 선택에 사용하는 비용 |
- Windows: `route print`로 조회.
- Linux: `ip route`로 조회.
- 기본 경로 `0.0.0.0/0`: 더 구체적으로 일치하는 경로가 없을 때 사용하는 경로.

경로 선택에서는 먼저 목적지와 가장 길게 일치하는 프리픽스를 찾는다. 단순히 메트릭이 가장 작은 경로부터 고르는 것은 아니다.

### 6. tcpdump — “실제로 어떤 패킷이 오가는가?”

네트워크 인터페이스에서 관찰 가능한 패킷을 캡처하고 내용을 분석한다.

- 통신 장애 원인 분석.
- 비정상 트래픽 및 공격 흔적 확인.
- 특정 호스트·포트·프로토콜만 선택해 분석.

| 옵션 | 의미 |
| --- | --- |
| `-i` | 캡처할 인터페이스 지정 |
| `-n` | 주소 등을 이름으로 변환하지 않고 숫자로 표시 |
| `-c` | 지정한 개수의 패킷을 캡처한 후 종료 |
| `-A` | 패킷 데이터를 ASCII로 표시 |
| `-w` | 캡처 결과를 파일로 저장 |
| `-r` | 저장된 캡처 파일 읽기 |

구분할 점:

- netstat: 연결 상태를 확인.
- tcpdump: 실제로 오가는 패킷을 확인.
- tcpdump를 실행한다고 같은 네트워크의 모든 통신을 볼 수 있는 것은 아니다.
- 암호화된 트래픽은 캡처해도 평문 내용을 바로 읽을 수 없다.

### 1. 네트워크 공격의 큰 분류

| 구분 | 수동적 공격 | 능동적 공격 |
| --- | --- | --- |
| 방식 | 통신 내용을 몰래 관찰·수집 | 데이터를 위조·변조하거나 서비스를 방해 |
| 주요 침해 | 기밀성 | 무결성·가용성·인증 |

| 탐지 | 통신에 변화를 주지 않아 탐지가 어려움 | 통신이나 시스템에 변화가 생겨 탐지 단서가 발생 |

수동적 공격도 정보 유출이라는 피해가 발생한다. 교재의 ‘직접적인 피해 없음’은 데이터를 직접 변경하거나 서비스를 중단시키지 않는다는 의미다.

---

### 2. DoS·DDoS·DRDoS 비교

모두 정상 사용자가 서비스를 이용하지 못하게 하는 가용성 공격이다.

| 구분 | 핵심 | 공격 흐름 |
| --- | --- | --- |
| DoS | 서비스 이용 방해 | 공격원 → 피해 서버 |
| DDoS | 여러 공격원에서 분산 공격 | 다수 공격원 → 피해 서버 |
| DRDoS | 다른 서버의 응답을 피해자에게 보내는 반사 공격 | 공격원 → 반사 서버들 → 피해 서버 |

DDoS의 대표적인 구조:

```
공격자 → C&C 서버 → 다수의 봇 → 피해 서버
          명령 전달     공격 수행
```

- 봇: 공격자의 명령에 따라 동작하는 악성 프로그램.
- 좀비 PC: 봇 등에 감염되어 공격에 이용되는 컴퓨터.
- 봇넷: 공격자가 통제하는 감염 기기들의 집합.
- C&C: 봇에 명령을 전달하고 통제하는 시스템.
- DNS 싱크홀: 악성 도메인 접속을 통제된 서버로 유도해 C&C 연결을 차단하고 감염 기기를 파악하는 기술.

DRDoS의 핵심:

```
공격자가 요청의 출발지 IP를 피해자 IP로 위조
                    ↓
여러 정상 서버가 피해자에게 응답
                    ↓
응답 트래픽이 피해자에게 집중
```

반사는 응답의 방향을 피해자에게 돌리는 것이고, 증폭은 요청보다 큰 응답을 발생시키는 것이다. 두 개념은 구분해야 한다.

---

### 3. SYN Flooding

TCP 연결이 완료되기 전의 대기 상태를 대량으로 만들어 서버의 연결 자원을 소진시키는 공격이다.

```
정상 연결
클라이언트 ── SYN ──→ 서버
클라이언트 ← SYN+ACK ─ 서버
클라이언트 ── ACK ──→ 서버 → 연결 완료

SYN Flooding
공격자 ── 다량의 SYN ──→ 서버
                         ↓
                  SYN+ACK 응답
                         ↓
                  마지막 ACK가 오지 않음
                         ↓
             Half-Open 연결이 누적되어 자원 소진
```

- 서버 상태: SYN_RECEIVED.
- 핵심 대상: 연결 대기 큐와 연결 관리 자원.
- 출발지 IP 위조가 흔히 이용되지만, 반드시 필요한 조건은 아니다.

| 대응 | 원리 |
| --- | --- |
| SYN Cookie | 연결 정보를 시퀀스 번호에 반영하고, 유효한 ACK가 온 뒤 연결 자원을 할당 |
| SYN 요청 제한 | 과도한 신규 연결 요청을 제한 |
| 대기 시간 조정 | 미완성 연결이 자원을 오래 점유하지 않도록 조정 |
| SYN Proxy | 중간 장비가 연결 절차를 대신 검증 |
| First SYN Drop | 첫 SYN을 버리고 재전송 여부를 확인하는 방식 |

SYN Cookie는 사용자의 신원을 인증하는 기술이 아니라, SYN+ACK에 대한 유효한 응답을 확인해 미완성 연결의 자원 점유를 줄이는 기술이다.

### 4. 대표적인 DoS 공격

| 공격 | 핵심 원리 | 구별 포인트 |
| --- | --- | --- |
| SYN Flooding | 미완성 TCP 연결을 대량 생성 | Half-Open, 연결 대기 큐 |
| UDP Flooding | UDP 패킷을 대량 전송 | 대역폭·패킷 처리 자원 소진 |
| ICMP Flooding | ICMP 패킷을 대량 전송 | 요청·응답 처리 부담 |
| Smurf | 피해자 IP로 위조한 ICMP 요청을 브로드캐스트로 전송 | 반사·증폭 |
| LAND | 출발지와 목적지 IP·포트를 피해자 것으로 동일하게 설정 | 자기 자신과 통신하는 형태 |
| Ping of Death | 재조립 결과가 IPv4 최대 길이를 넘는 비정상 패킷 이용 | 크기·재조립 처리 취약점 |
| Teardrop | IP 단편의 오프셋을 비정상적으로 만들어 재조립 오류 유발 | 단편 중첩·오프셋 |

Smurf의 흐름:

```
공격자
  │ 출발지 IP = 피해자 IP
  │ 목적지 = 증폭 네트워크의 브로드캐스트 주소
  ↓
여러 호스트가 ICMP 요청 수신
  ↓
피해자에게 ICMP 응답 집중
```

주요 대응 원리:

- 출발지 IP 위조 패킷 필터링.
- IP Directed Broadcast 전달 제한.
- 브로드캐스트 ICMP 요청에 대한 응답 제한.
- 비정상 단편 검사와 취약점 패치.

Ping of Death의 65,535바이트는 ICMP 데이터만의 한도가 아니라 IPv4 데이터그램 전체 길이의 최대값이다.

### 5. DDoS를 ‘무엇을 소진시키는가’로 구분

| 구분 | 소진 대상 | 대표 공격 | 주요 관찰 지표 |
| --- | --- | --- | --- |
| 대역폭 공격 | 네트워크 회선 용량 | UDP·ICMP Flood, 반사·증폭 공격 | bps |
| 프로토콜·연결 자원 공격 | 연결 테이블, 패킷 처리 능력 | SYN Flood 등 | pps, 연결 수 |
| 애플리케이션 공격 | 웹서버·DB·작업 처리 자원 | HTTP Flood, Slow HTTP | 요청 수, 응답 시간, 동시 연결 수 |
- bps: 초당 전송되는 비트 수.
- pps: 초당 처리되는 패킷 수.
- 적은 트래픽으로도 연결이나 처리 자원을 오래 점유하면 서비스 거부가 발생할 수 있다.

---

### 6. HTTP 기반 서비스 거부 공격

| 공격 | 동작 | 서버가 부담을 받는 이유 |
| --- | --- | --- |
| HTTP GET/POST Flooding | 정상 형식의 요청을 대량 전송 | 웹 처리·DB 조회 작업 증가 |
| Slowloris | HTTP 헤더를 끝내지 않고 조금씩 전송 | 요청이 완료되기를 기다리며 연결 유지 |
| Slow HTTP POST, RUDY | 요청 본문을 매우 느리게 전송 | 본문 수신이 끝나지 않아 연결 유지 |
| Slow HTTP Read | 서버 응답을 매우 느리게 수신 | 서버의 송신 버퍼·연결 자원 점유 |
| CC Attack | 캐시를 활용하기 어렵게 하여 원본 서버 처리 유도 | 캐시 효과 감소, 원본 서버 부하 증가 |
| 동적 HTTP Request Flooding | 요청 URL·매개변수를 계속 변경 | 단순 차단·캐시 처리를 어렵게 함 |
| HashDoS | 해시 충돌을 유발하는 입력 이용 | 해시 테이블 처리에 CPU 자원 과다 사용 |

```
Slowloris   = 요청 헤더를 천천히 보냄
Slow POST   = 요청 본문을 천천히 보냄
Slow Read   = 서버 응답을 천천히 받음
```

주요 대응은 요청 완료 시간 제한, 최소 전송률 설정, 동시 연결·요청 수 제한, 비정상 요청 탐지다. 회선 자체가 포화된 공격은 서버 내부의 차단만으로 해결하기 어렵다.

### 7. 스캐닝

시스템의 동작 여부, 열린 포트, 서비스·운영체제 등의 정보를 확인하는 행위다. 보안 점검에도 쓰이며 공격 전 정보 수집에도 이용된다.

| 단계 | 의미 |
| --- | --- |
| 풋프린팅 | 공개 자료 등을 이용해 대상의 기초 정보 수집 |
| 스캐닝 | 호스트·포트·서비스의 상태 확인 |
| 목록화, Enumeration | 계정·공유 자원·서비스 설정 등 상세 정보 수집 |

주요 포트 스캔 비교:

| 종류 | 보내는 패킷·방식 | 열린 포트의 대표 반응 | 닫힌 포트의 대표 반응 |
| --- | --- | --- | --- |
| TCP Connect | TCP 연결을 끝까지 수립 | SYN+ACK 수신 후 ACK로 연결 완료 | RST |
| TCP SYN, Half-Open | SYN 전송 후 연결을 끝까지 완료하지 않음 | SYN+ACK 수신 후 스캐너가 RST | RST |
| FIN | FIN 플래그 설정 | 일반적으로 무응답 | RST |
| NULL | TCP 플래그를 설정하지 않음 | 일반적으로 무응답 | RST |
| XMAS | FIN·PSH·URG 설정 | 일반적으로 무응답 | RST |
| UDP | UDP 패킷 전송 | 서비스 응답 또는 무응답 | ICMP Port Unreachable |

주의할 점:

- 무응답만으로 ‘열림’을 확정할 수 없다. 방화벽 차단이나 패킷 손실일 수도 있다.
- FIN·NULL·XMAS의 반응은 운영체제 구현에 따라 다를 수 있다.
- SYN 스캔도 방화벽·IDS 등에 탐지될 수 있다. ‘로그가 절대 남지 않는다’는 뜻이 아니다.
- XMAS 스캔은 모든 TCP 플래그를 켜는 것이 아니다.

### 8. 스니핑

네트워크를 흐르는 다른 사용자의 통신 내용을 몰래 수집하는 행위다.

| 환경 | 특징 |
| --- | --- |
| 허브 | 수신한 신호를 다른 포트로 전달하므로 다른 기기의 트래픽을 관찰하기 쉬움 |
| 스위치 | 목적지 MAC 주소에 해당하는 포트로 전달하므로 다른 기기의 유니캐스트 트래픽이 기본적으로 보이지 않음 |

Promiscuous Mode는 NIC에 도착한 프레임을 목적지 MAC 주소가 자신과 달라도 수신하도록 하는 모드다.

이 모드를 켠다고 스위치의 모든 트래픽이 자동으로 자신의 포트에 전달되는 것은 아니다.

스위치 환경에서 트래픽을 가로채는 데 이용되는 방식:

| 방식 | 핵심 |
| --- | --- |
| MAC Flooding | 다량의 MAC 주소로 스위치의 MAC 테이블을 채워 비정상 전달을 유도 |
| ARP Spoofing | IP와 MAC의 대응 관계를 속여 공격자에게 트래픽 유도 |
| ICMP Redirect 악용 | 잘못된 경로 정보를 주입해 트래픽 경로 변경 |
| 포트 미러링 악용 | 관리용 트래픽 복사 기능에 접근해 통신 수집 |

MAC Flooding이 성공하면 스위치가 무조건 허브처럼 동작하는 것은 아니며, 장비의 구현과 설정에 따라 결과가 달라진다.

방어의 핵심은 통신 암호화, 스위치 접근 통제, MAC 학습 제한, ARP 검증이다.

---

### 9. 스푸핑

주소나 신원을 위조해 다른 대상인 것처럼 속이는 공격이다.

| 종류 | 속이는 정보 | 주요 결과 |
| --- | --- | --- |
| ARP Spoofing | IP ↔ MAC 대응 관계 | 같은 LAN에서 통신 가로채기 |
| IP Spoofing | 패킷의 출발지 IP | 신뢰 관계 악용, 반사 공격 |
| DNS Spoofing | 도메인 ↔ IP 응답 | 가짜 사이트로 접속 유도 |
| 이메일 Spoofing | 이메일 발신자 정보 | 사칭·피싱 |

ARP Spoofing의 핵심:

```
정상 ARP 캐시
게이트웨이 IP → 실제 게이트웨이 MAC

오염된 ARP 캐시
게이트웨이 IP → 공격자 MAC

결과
피해자 → 공격자 → 실제 게이트웨이
```

피해자는 정상 게이트웨이로 보낸다고 생각하지만, 실제 프레임은 공격자에게 전달된다.

헷갈리기 쉬운 테이블:

| 테이블 | 저장하는 대응 관계 | 주로 사용하는 장치 |
| --- | --- | --- |
| ARP 캐시 | IP 주소 ↔ MAC 주소 | 호스트·라우터 |
| MAC 테이블 | MAC 주소 ↔ 스위치 포트 | L2 스위치 |
| 라우팅 테이블 | 목적지 네트워크 ↔ 다음 홉·출력 인터페이스 | 호스트·라우터 |
- ARP Spoofing은 ARP 캐시를 오염시킨다.
- MAC Flooding은 스위치의 MAC 테이블을 대상으로 한다.

---

### 10. 스푸핑·스니핑 대응

| 위협 | 핵심 대응 |
| --- | --- |
| ARP Spoofing | 정적 ARP 등록, DAI 같은 ARP 검증, IP·MAC 변경 감시 |
| IP Spoofing | 출발지 주소 필터링, uRPF, IP 주소만을 믿는 인증 방식 제거 |
| DNS Spoofing | DNS 응답 검증, DNSSEC 검증, HTTPS 인증서 검증 |
| 스니핑 | TLS·SSH·VPN 등으로 통신 암호화 |
| MAC Flooding | Port Security 등으로 포트별 MAC 학습 수 제한 |
| 세션 탈취 | 세션 토큰 보호, 만료·폐기 관리, 중요 작업 재인증 |

ARPwatch는 IP와 MAC의 대응 관계 변화를 감시하는 도구다. 변화가 탐지되었다고 반드시 공격인 것은 아니므로 정상 장비 변경과 구분해야 한다.

### 11. 세션 하이재킹

인증이 끝난 정상 사용자의 세션을 가로채 그 사용자처럼 통신하는 공격이다.

```
정상 사용자 ── 로그인·인증 ──→ 서버
                 ↓
            유효한 세션 생성
                 ↓
공격자가 세션 정보 탈취·악용
                 ↓
공격자 ── 정상 사용자로 가장 ──→ 서버
```

| 구분 | 악용하는 정보 | 핵심 |
| --- | --- | --- |
| TCP 세션 하이재킹 | TCP 순서 번호·확인응답 번호 등 | 기존 TCP 연결에 패킷을 끼워 넣거나 통신을 장악 |
| HTTP 세션 하이재킹 | 세션 ID·쿠키·토큰 | 로그인된 사용자의 권한으로 요청 |

TCP 세션 하이재킹의 탐지 단서:

- 순서 번호의 비정상적인 변화.
- ACK Storm.
- 재전송·패킷 손실 증가.
- 예상하지 않은 연결 초기화.

이런 현상은 공격의 단서이지, 단독으로 공격을 확정하는 증거는 아니다.

HTTP 세션 보호의 핵심:

- HTTPS 사용.
- 쿠키에 Secure·HttpOnly·SameSite 속성 적용.
- 로그인 시 세션 ID 재발급.
- 로그아웃·만료 시 서버에서 세션 무효화.
- 중요 작업에서 재인증.

스푸핑은 ‘신원을 속이는 것’, 스니핑은 ‘통신을 엿보는 것’, 세션 하이재킹은 ‘이미 인증된 통신을 빼앗는 것’으로 구분하면 된다.

### 1. IDS와 IPS의 기본 개념

IDS는 침입을 탐지해 알리는 시스템이고, IPS는 탐지한 공격을 직접 차단하는 시스템이다.

| 구분 | IDS | IPS |
| --- | --- | --- |
| 명칭 | 침입 탐지 시스템 | 침입 방지 시스템 |
| 핵심 역할 | 공격 탐지·기록·경고 | 공격 탐지·차단 |
| 일반적인 배치 | 통신 경로 옆에서 복사된 트래픽 분석 | 통신 경로 중간에 인라인으로 배치 |
| 공격 발견 시 | 관리자에게 경고 | 패킷 폐기, 연결 차단 등 |
| 오탐의 영향 | 불필요한 경고와 분석 업무 증가 | 정상 통신까지 차단될 수 있음 |

IDS의 기본 처리 흐름:

```
데이터 수집 → 가공·축약·필터링 → 침입 분석·탐지 → 보고·대응
```

- 수집: 패킷, 시스템 로그, 사용자 활동 등을 모음.
- 가공: 불필요한 정보를 줄이고 분석할 형태로 정리.
- 탐지: 공격 패턴이나 정상 행동 기준과 비교.
- 대응: 경고·기록, 다른 보안 장비와 연동.

IDS도 다른 장비에 차단을 요청할 수 있지만, 기본적인 구분은 ‘탐지 중심’과 ‘직접 차단’이다.

---

### 2. 탐지 방법에 따른 분류: 오용 탐지와 이상 탐지

| 구분 | 오용 탐지(Misuse) | 이상 탐지(Anomaly) |
| --- | --- | --- |
| 다른 이름 | 지식 기반·시그니처 기반 | 정상 프로파일 기반·비정상 행위 탐지 |
| 비교 기준 | 이미 알려진 공격 패턴 | 평소의 정상 행동 |
| 판단 방식 | 공격 패턴과 일치하면 탐지 | 정상 범위를 벗어나면 탐지 |
| 장점 | 알려진 공격을 정확하게 탐지, 상대적으로 오탐이 적음 | 알려지지 않은 공격도 탐지할 가능성 |
| 단점 | 새로운 공격이나 변형된 공격을 놓칠 수 있음 | 정상적인 변화도 공격으로 오인할 수 있음 |
| 관리 사항 | 공격 패턴을 지속적으로 갱신 | 정상 기준 학습·갱신 및 임계치 조정 |

예시:

- 오용 탐지: “이 요청에는 등록된 공격 문자열이 있으니 공격이다.”
- 이상 탐지: “평소 하루 3회 로그인하던 계정이 1분에 500회 시도하니 의심스럽다.”

암기할 때는 다음처럼 구분하면 된다.

```
오용 탐지 → 공격의 모습을 알고 비교
이상 탐지 → 정상의 모습을 알고 비교
```

이상 탐지가 반드시 AI를 사용하는 것은 아니다. 통계와 임계치로도 구현할 수 있으며, 새로운 공격을 모두 탐지하는 것도 아니다.

---

### 3. 오탐과 미탐

여기서 Positive는 ‘공격이라고 판단’, Negative는 ‘정상이라고 판단’을 뜻한다.

| 실제 상태 | 공격이라고 판단 | 정상이라고 판단 |
| --- | --- | --- |
| 실제 공격 | TP: 정상 탐지 | FN: 미탐 |
| 실제 정상 | FP: 오탐 | TN: 정상 판정 |
- FP(False Positive, 오탐): 정상 사용자를 공격자로 잘못 판단.
- FN(False Negative, 미탐): 실제 공격을 정상으로 판단해 놓침.

예시:

```
정상적인 대용량 다운로드를 공격으로 경고 → 오탐(FP)
실제 정보 유출을 정상 다운로드로 판단 → 미탐(FN)
```

일반적으로 탐지 기준을 민감하게 하면 미탐은 줄지만 오탐이 늘 수 있다. 특히 IPS의 오탐은 정상 서비스 차단으로 이어질 수 있어 중요하다.

---

### 4. 데이터 수집 위치에 따른 분류: HIDS와 NIDS

| 구분 | HIDS: 호스트 기반 | NIDS: 네트워크 기반 |
| --- | --- | --- |
| 설치 위치 | 개별 서버·PC | 네트워크의 트래픽 관찰 지점 |
| 주요 분석 대상 | 시스템 로그, 파일 변경, 프로세스, 사용자 활동 | 네트워크 패킷과 통신 흐름 |
| 감시 범위 | 설치된 호스트 내부 | 관찰 가능한 네트워크 구간 |
| 장점 | 실제 파일 변조나 내부 행위를 자세히 확인 | 여러 호스트의 통신을 함께 감시 |
| 단점 | 호스트 자원 사용, 개별 설치·관리 필요 | 대량 트래픽 처리 부담, 호스트 내부 상황 파악에 한계 |
| 암호화 통신 | 호스트에서 복호화된 데이터나 관련 활동을 관찰할 수 있음 | 복호화하지 않으면 암호화된 본문 분석이 어려움 |
- HIDS 예: 중요 파일의 해시값을 비교하여 변조 여부 확인.
- NIDS 예: 네트워크에서 포트 스캔이나 공격 패턴이 포함된 패킷 탐지.

스위치 환경의 NIDS는 SPAN·포트 미러링이나 TAP 등을 이용해 분석할 트래픽을 전달받는다.

두 분류 기준은 서로 독립적이다.

```
어디서 수집하나? → HIDS / NIDS
무엇과 비교하나? → 오용 탐지 / 이상 탐지
```

따라서 HIDS와 NIDS 모두 오용 탐지와 이상 탐지를 사용할 수 있다. NIDS라는 이유만으로 오탐이 높다고 단정하면 안 된다.

### 5. 방화벽·IDS·IPS 비교

| 구분 | 방화벽 | IDS | IPS |
| --- | --- | --- | --- |
| 핵심 질문 | 허용된 통신인가? | 공격이나 침입 징후가 있는가? | 공격이면 통과를 막을 것인가? |
| 주된 역할 | 접근 정책에 따른 허용·차단 | 침입 탐지와 경고 | 침입 탐지와 차단 |
| 판단 기준 | IP, 포트, 연결 상태, 애플리케이션 등 | 공격 패턴, 정상 행동 기준 등 | 공격 패턴, 정상 행동 기준 등 |
| 주요 한계 | 허용된 통신 안의 공격을 놓칠 수 있음 | 탐지만으로 공격을 막지는 못함 | 오탐 시 정상 통신 차단, 처리 지연 가능 |

```
방화벽 → 출입 규칙 확인
IDS    → 수상한 행동 발견 후 경고
IPS    → 수상한 행동 발견 후 차단
```

교재의 비교는 전통적인 역할 구분이다. 실제 제품은 방화벽에 IPS 기능이 포함되는 등 기능이 겹칠 수 있다.

### 6. 허니팟(Honeypot)

공격자를 유인하기 위해 만든 미끼 시스템이다. 공격자가 접근하거나 공격하는 과정을 관찰하여 공격 기법과 침입 흔적을 수집한다.

```
공격자 → 미끼 시스템에 접근 → 행동 기록·분석 → 탐지·대응에 활용
```

- 목적: 공격 유인, 공격 행위 관찰, 정보 수집.
- 특징: 실제 시스템처럼 보이도록 서비스와 데이터를 구성.
- 장점: 정상 업무 이용이 거의 없어 접근 자체가 의심 신호가 되기 쉬움.
- 한계: 허니팟에 접근하지 않은 공격은 관찰하기 어려움.
- 주의점: 침해된 허니팟이 다른 시스템을 공격하는 경유지가 되지 않도록 격리와 외부 통신 통제가 필요.

허니팟은 실제 업무 서버를 대신하는 시스템이 아니라, 공격을 관찰하기 위한 미끼다.

---

### 7. Snort 규칙의 기본 구조

Snort는 규칙을 이용해 네트워크 트래픽을 분석하는 도구로, 구성에 따라 IDS 또는 IPS로 사용할 수 있다.

규칙은 ‘헤더 + 옵션’으로 구성된다.

```
동작 프로토콜 출발지IP 출발지포트 방향 목적지IP 목적지포트 (옵션)
```

| 구성 | 의미 |
| --- | --- |
| 동작 | 경고, 기록, 차단 등 수행할 작업 |
| 프로토콜 | TCP, UDP, ICMP 등 |
| 출발지·목적지 | 검사할 IP와 포트 범위 |
| 방향 | 트래픽의 진행 방향 |
| 옵션 | 탐지 조건과 경고 메시지 등 |

주요 옵션:

| 옵션 | 의미 |
| --- | --- |
| msg | 경고 메시지 |
| content | 찾을 문자열 또는 바이트 패턴 |
| offset | 패턴 검색을 시작할 위치 |
| depth | 패턴을 검색할 범위 |
| nocase | 대소문자 구분 없이 검색 |
| flow | 연결 상태와 통신 방향 등의 조건 |
| sid | 규칙 식별 번호 |
| rev | 규칙 수정 버전 |

규칙의 동작이 `alert`이면 경고를 발생시킨다. 규칙을 작성했다는 이유만으로 패킷이 차단되는 것은 아니며, 차단하려면 IPS 동작 구성과 차단 규칙이 필요하다.

### 1. 방화벽(Firewall)의 개념

네트워크 사이에서 보안정책에 따라 트래픽을 허용하거나 차단하는 시스템이다.

```
외부 네트워크 → 방화벽의 정책 검사 → 내부 네트워크
                     ├─ 허용 → 전달
                     └─ 차단 → 폐기 또는 거부 응답
```

- 접근제어: 출발지·목적지 IP, 포트, 프로토콜 등을 기준으로 통신 통제
- 로그 및 감사: 접속과 차단 내역을 기록하여 분석에 활용
- 정책의 일관된 적용: 방화벽을 통과하는 트래픽에 동일한 보안정책 적용
- 제품에 따라 사용자 인증, VPN, 응용 프로그램 검사 등을 추가 제공

방화벽은 외부와 내부 사이뿐 아니라 내부 부서·서버 구간 사이에도 설치할 수 있다.

주의할 한계:

- 방화벽을 우회하는 통신은 통제할 수 없다.
- 허용된 통신에 포함된 공격까지 모두 차단하는 것은 아니다.
- 내부자 공격이나 악성코드에 대한 보호는 방화벽만으로 충분하지 않다.

---

### 2. 방화벽 운영 정책

| 구분 | Deny All 정책 | Permit All 정책 |
| --- | --- | --- |
| 기본 원칙 | 기본 차단, 필요한 것만 허용 | 기본 허용, 금지할 것만 차단 |
| 허용 기준 | 명시적으로 허용된 통신 | 명시적으로 금지되지 않은 통신 |
| 장점 | 불필요하거나 예상하지 못한 접근 제한 | 서비스 이용이 편리 |
| 단점 | 필요한 허용 규칙을 빠짐없이 관리해야 함 | 차단 규칙에 없는 위험한 통신이 허용될 수 있음 |
| 암기 | 허용 목록 방식 | 차단 목록 방식 |

예시:

```
Deny All
→ 웹 서버의 HTTPS 접속만 허용
→ 나머지는 차단

Permit All
→ Telnet 접속만 차단
→ 나머지는 허용
```

두 정책은 기본 처리 방식을 뜻한다. 인바운드·아웃바운드 중 어느 방향에만 사용하는 정책으로 고정되는 것은 아니다.

---

### 3. 검사 방식에 따른 방화벽 분류

| 구분 | 패킷 필터링 | 상태 기반 검사 | 응용 수준 프록시 | 회선 수준 프록시 |
| --- | --- | --- | --- | --- |
| 검사 기준 | 패킷 헤더 | 패킷 헤더 + 연결 상태 | 응용 프로토콜과 메시지 내용 | 연결 설정과 세션 정보 |
| 핵심 | 개별 패킷 검사 | 기존 통신의 정상적인 후속 패킷인지 검사 | 서비스 내용을 이해하고 검사 | 연결을 중계하고 통제 |
| 장점 | 단순하고 처리 부담이 적음 | 통신 흐름을 고려한 통제 | 서비스별 정밀한 통제 | 응용 수준 프록시보다 처리 부담이 적음 |
| 한계 | 연결 맥락과 내용 파악에 한계 | 상태 테이블 관리 필요 | 처리 부담과 서비스별 지원 필요 | 응용 데이터 내용 검사에 한계 |

패킷 필터링

- 주로 네트워크·전송 계층의 헤더를 검사한다.
- 출발지·목적지 IP, 출발지·목적지 포트, 프로토콜, 방향, TCP 플래그 등을 활용한다.
- 기본적인 비상태형 방식은 이전 패킷과의 관계를 기억하지 않는다.

```
“목적지 포트가 443인가?”
→ 개별 패킷의 조건으로 판단
```

상태 기반 검사(Stateful Inspection)

- 연결 상태를 상태 테이블에 저장한다.
- 들어온 패킷이 허용된 연결에 속하는지, 연결 상태에 맞는지 확인한다.
- 내부에서 시작한 허용된 요청에 대한 응답을 구분할 수 있다.

```
내부 PC → 외부 서버: 연결 요청
방화벽: 허용한 연결 정보를 기록

외부 서버 → 내부 PC: 응답
방화벽: 기록된 연결의 응답인지 확인
```

TCP의 ACK 플래그가 있다는 이유만으로 정상 응답이라고 판단하는 것과는 다르다. 또한 상태 기반 검사 자체가 모든 응용 데이터의 정밀 분석을 뜻하지는 않는다.

프록시 방화벽

클라이언트와 서버 사이에서 연결을 대신 맺고 데이터를 중계한다.

```
클라이언트 ↔ 프록시 ↔ 서버
          연결 1   연결 2
```

- 응용 수준 프록시: HTTP·FTP 등의 의미와 내용을 이해하고 검사한다.
- 회선 수준 프록시: 연결 설정과 세션을 통제하며, 응용 내용은 깊게 검사하지 않는다. 대표적으로 SOCKS가 있다.

### 4. NAT와 PAT

NAT(Network Address Translation)는 패킷의 IP 주소를 변환하는 기능이다.

| 구분 | 핵심 | 예시 |
| --- | --- | --- |
| Static NAT | 고정된 1:1 주소 매핑 | 내부 서버 하나를 공인 IP 하나에 대응 |
| Dynamic NAT | 공인 IP 풀에서 동적으로 주소 할당 | 통신할 때 사용 가능한 공인 IP를 배정 |
| PAT | IP 주소와 포트를 함께 변환 | 여러 내부 기기가 공인 IP 하나를 공유 |

PAT의 동작 예시:

```
내부 PC A: 192.168.0.10:50000 → 공인 IP:40001
내부 PC B: 192.168.0.20:50000 → 공인 IP:40002
```

같은 공인 IP를 사용하더라도 변환된 포트 번호로 각 통신을 구분한다. 응답이 오면 변환 테이블을 보고 원래 내부 기기에 전달한다.

- SNAT: 출발지 주소 변환
- DNAT: 목적지 주소 변환. 외부 요청을 내부 서버로 전달할 때 활용
- NAT는 주소 변환 기능이며, 암호화나 공격 탐지를 제공하는 기능은 아니다.

---

### 5. 베스천 호스트와 DMZ

| 구분 | 의미 | 역할 |
| --- | --- | --- |
| 베스천 호스트(Bastion Host) | 외부 공격에 대비해 보안을 강화한 호스트 | 프록시·접근 중계 등 보안상 중요한 기능 수행 |
| DMZ | 외부망과 내부망 사이에 분리한 네트워크 구간 | 외부 공개 서버와 내부 중요 자원 분리 |

베스천 호스트는 불필요한 서비스와 계정을 줄이고, 접근제어와 로그 관리를 강화한 시스템이다.

DMZ에는 웹·메일·DNS 등 외부에서 접근해야 하는 서버를 배치할 수 있다.

```
인터넷 ↔ DMZ의 공개 서버
              │
        필요한 통신만 허용
              │
           내부망
```

DMZ의 목적은 공개 서버가 침해되더라도 내부망으로 쉽게 접근하지 못하게 하는 것이다. DMZ에서 내부망으로의 접근도 제한해야 한다.

### 6. 방화벽 구성 방식

| 구성 | 구조의 핵심 | 장점 | 한계 |
| --- | --- | --- | --- |
| 스크리닝 라우터 | 라우터의 패킷 필터링으로 통제 | 구조가 단순 | 정밀한 검사와 다중 방어에 한계 |
| 듀얼 홈드 호스트 | 네트워크 인터페이스가 2개인 호스트가 중계 | 내·외부 직접 통신 차단 | 중계 호스트에 의존 |
| 스크린드 호스트 | 스크리닝 라우터 + 베스천 호스트 | 필터링과 호스트 보안의 다중 방어 | 라우터 정책이나 베스천 침해에 영향받음 |
| 스크린드 서브넷 | 외부망과 내부망 사이에 별도 DMZ 구성 | 공개 서버 격리, 방어 단계 증가 | 구축·관리 복잡성 증가 |

스크리닝 라우터:

```
외부망 ↔ [패킷 필터링 라우터] ↔ 내부망
```

듀얼 홈드 호스트:

```
외부망 ↔ [외부 NIC | 중계 호스트 | 내부 NIC] ↔ 내부망
```

- NIC는 네트워크 인터페이스를 뜻한다.
- 전통적인 구조에서는 IP 포워딩을 비활성화한다.
- 패킷을 그대로 라우팅하지 않고 프록시 등으로 통신을 중계한다.

스크린드 호스트:

```
외부망 ↔ [스크리닝 라우터] ↔ 내부망
                                └─ [베스천 호스트]
```

- 라우터는 외부 통신이 베스천 호스트를 거치도록 제한한다.
- 베스천 호스트가 인증·프록시 등의 추가 통제를 담당한다.

스크린드 서브넷:

```
외부망 ↔ [외부 필터] ↔ DMZ ↔ [내부 필터] ↔ 내부망
                       └─ 공개 서버·베스천 호스트
```

- 외부망·DMZ·내부망을 서로 분리한다.
- DMZ가 침해되어도 내부망 앞에 추가 통제 지점이 남는다.
- 두 장비로 구성하거나, 인터페이스가 여러 개인 방화벽으로 구간을 분리할 수 있다.

---

### 7. iptables 핵심

iptables에서는 패킷이 해당 리눅스 시스템과 어떤 관계인지에 따라 체인을 구분한다.

| 체인 | 검사 대상 |
| --- | --- |
| INPUT | 이 시스템을 목적지로 하는 패킷 |
| OUTPUT | 이 시스템이 직접 생성한 패킷 |
| FORWARD | 이 시스템을 거쳐 다른 시스템으로 전달되는 패킷 |

```
방화벽 자신에게 도착 → INPUT
방화벽 자신이 생성   → OUTPUT
방화벽을 통과       → FORWARD
```

INPUT은 단순히 ‘외부에서 들어오는 모든 패킷’을 뜻하지 않는다. 내부 서버로 전달하기 위해 방화벽을 통과하는 패킷은 FORWARD에 해당한다.

| 처리 | 의미 |
| --- | --- |
| ACCEPT | 허용 |
| DROP | 응답 없이 폐기 |
| REJECT | 거부 응답을 보내며 차단 |

규칙은 순서가 중요하다. 앞에서 최종 허용·차단이 결정되면 뒤의 규칙까지 검사하지 않으므로, 넓은 허용 규칙 때문에 뒤의 차단 규칙이 적용되지 않는 상황을 주의해야 한다.

### 1. VPN의 개념과 기능

VPN(Virtual Private Network)은 인터넷 같은 공중망 위에 논리적인 사설 통신망을 구성하는 기술이다.

예를 들어 본사와 지사가 멀리 떨어져 있어도 VPN을 통해 내부망끼리 연결할 수 있다.

```
본사 내부망 ─ VPN 장비 ═══ 인터넷상의 VPN 터널 ═══ VPN 장비 ─ 지사 내부망
```

| 기능 | 의미 |
| --- | --- |
| 기밀성 | 데이터를 암호화하여 제3자가 내용을 읽지 못하게 함 |
| 무결성 | 전송 중 데이터가 변경되었는지 검증 |
| 데이터 근원 인증 | 데이터가 정당한 송신자로부터 왔는지 확인 |
| 접근 통제 | 인증된 사용자에게 허용된 자원만 접근하도록 제한 |
| 재전송 공격 방지 | 이미 수신한 패킷을 공격자가 다시 보내는 것을 탐지·거부 |

터널링은 원래 패킷을 다른 패킷 안에 넣어 운반하는 캡슐화 기술이다. 터널링 자체가 암호화를 의미하지는 않는다.

---

### 2. VPN 연결 형태

| 형태 | 연결 대상 | 예시 |
| --- | --- | --- |
| Site-to-Site | 네트워크 ↔ 네트워크 | 본사와 지사 연결 |
| Remote Access | 사용자 단말 ↔ 사내망 | 재택근무자가 회사에 접속 |
| Host-to-Host | 호스트 ↔ 호스트 | 두 서버 사이의 통신 보호 |

Site-to-Site에서는 보통 양쪽 VPN 게이트웨이가 암호화·복호화를 처리한다. 따라서 내부 단말마다 VPN 기능을 구현할 필요가 없다.

단, 게이트웨이 사이만 보호한다면 단말에서 게이트웨이까지의 구간은 별도의 보호가 필요하다.

---

### 3. VPN 관련 기술 비교

| 기술 | 핵심 특징 | 구분할 점 |
| --- | --- | --- |
| PPTP | PPP를 터널링하는 전통적인 기술 | 보안상 취약한 구형 방식 |
| L2TP | PPP 프레임을 터널링 | 자체 데이터 암호화 기능이 없어 IPsec과 결합 |
| IPsec | 네트워크 계층에서 IP 패킷 보호 | 응용프로그램과 독립적으로 적용 가능 |
| SSL VPN | TLS를 이용하여 원격접속 통신 보호 | 웹 서비스 접근 또는 클라이언트 기반 터널 제공 |
| MPLS VPN | 통신사업자 망에서 레이블과 논리적 분리로 VPN 구성 | 자체적으로 데이터 암호화를 보장하지 않음 |

교재의 ‘SSL VPN’이라는 명칭은 일반적으로 TLS 기반 VPN까지 포함해 사용한다.

IPsec VPN과 SSL VPN의 차이:

| 구분 | IPsec VPN | SSL VPN |
| --- | --- | --- |
| 보호 기준 | IP 패킷 | TLS 연결을 통한 통신 |
| 대표 용도 | 본사·지사 연결, 원격접속 | 사용자 원격접속 |
| 접근 범위 | 네트워크 단위 접근에 적합 | 특정 애플리케이션 단위 접근에 적합 |
| 단말 지원 | OS 내장 기능 또는 VPN 클라이언트 사용 | 웹 방식은 브라우저, 전체 터널은 클라이언트가 필요할 수 있음 |

‘IPsec은 무조건 별도 프로그램 필요’, ‘SSL VPN은 무조건 브라우저만으로 가능’으로 외우면 안 된다.

---

### 4. IPsec의 구성: AH·ESP·IKE·SA

IPsec은 IP 계층에서 통신을 보호하는 보안 프로토콜 모음이다.

| 구성요소 | 역할 |
| --- | --- |
| AH | 데이터 무결성·근원 인증, 재전송 공격 방지 지원 |
| ESP | 데이터 암호화, 무결성·근원 인증, 재전송 공격 방지 지원 |
| IKE | 통신 상대 인증, 키 교환, 보안 설정 협상 |
| SA | 통신에 적용할 보안 설정을 정리한 단방향 보안 연결 |

```
IKE로 상대 인증·키 교환·보안 설정 협상
                    ↓
                   SA 생성
                    ↓
          AH 또는 ESP로 실제 패킷 보호
```

AH와 ESP는 함께 사용할 수도 있지만, 반드시 둘을 동시에 사용해야 하는 것은 아니다.

---

### 5. AH와 ESP 비교

| 구분 | AH | ESP |
| --- | --- | --- |
| 암호화 | 제공하지 않음 | 제공 가능 |
| 무결성·근원 인증 | 제공 | 설정·알고리즘에 따라 제공 |
| 재전송 공격 방지 | 순서번호로 지원 | 순서번호로 지원 |
| IP 헤더 보호 | 변경되지 않는 필드 등을 인증 범위에 포함 | 바깥쪽 IP 헤더는 보호하지 않음 |
| 핵심 | 내용이 변조되었는지 확인 | 내용을 숨기고 변조 여부도 확인 가능 |
- AH는 암호화하지 않으므로 데이터 내용이 보인다.
- ESP는 암호화와 인증을 함께 제공하는 구성이 가능하다.
- AH는 IP 헤더도 인증하므로 주소를 변경하는 NAT와 충돌한다.
- ESP는 NAT-T를 이용해 NAT 환경을 통과할 수 있다.

재전송 공격 방지는 순서번호와 수신 윈도우를 이용해 이미 받은 패킷인지 확인하는 방식이다.

---

### 6. IPsec 전송 모드와 터널 모드

| 구분 | 전송 모드 | 터널 모드 |
| --- | --- | --- |
| 캡슐화 대상 | 원래 IP 패킷의 페이로드 | 원래 IP 패킷 전체 |
| 원래 IP 헤더 | 바깥쪽에 그대로 사용 | 새 패킷 내부에 포함 |
| 새로운 IP 헤더 | 추가하지 않음 | 추가함 |
| 대표 용도 | 호스트 ↔ 호스트 | 게이트웨이 ↔ 게이트웨이, 원격접속 |
| 오버헤드 | 상대적으로 작음 | 새 IP 헤더 때문에 더 큼 |

ESP를 기준으로 보면 다음과 같다.

```
원래 패킷
[원래 IP 헤더][TCP/UDP 헤더 + 데이터]

ESP 전송 모드
[원래 IP 헤더][ESP 헤더][암호화된 TCP/UDP 헤더 + 데이터 + 트레일러][인증값]

ESP 터널 모드
[새 IP 헤더][ESP 헤더][암호화된 원래 IP 패킷 + 트레일러][인증값]
```

터널 모드에서는 주소의 역할도 구분해야 한다.

- 원래 IP 헤더: 실제 송신 단말과 수신 단말의 주소
- 새 IP 헤더: VPN 터널 양 끝의 주소

```
본사 PC → 본사 VPN 장비 → 인터넷 → 지사 VPN 장비 → 지사 PC

원래 IP: 본사 PC → 지사 PC
새 IP:   본사 VPN 장비 → 지사 VPN 장비
```

터널 모드라도 AH만 사용하면 원래 패킷을 암호화하지 않는다. 원래 IP 주소까지 숨기는 것은 ESP 암호화를 적용했을 때다.

---

### 7. SA와 IKE

SA(Security Association)는 ‘어떤 방식으로 패킷을 보호할지’ 정한 보안 설정의 묶음이다.

주요 내용은 암호·인증 알고리즘, 키, 전송/터널 모드, 유효기간, 순서번호 등이다.

- IPsec SA는 단방향이다. IKE SA는 양방향 협상 통로이므로 구분한다.
- 양방향 통신에는 보통 송신용·수신용 SA가 각각 필요하다.
- AH와 ESP를 모두 적용하면 각각의 SA가 필요하다.
- SA 정보는 SAD(Security Association Database)에 저장한다.

| 용어 | 의미 |
| --- | --- |
| SPI | 패킷에 적용된 SA를 찾기 위한 식별값 |
| SAD | 실제 SA의 키·알고리즘 등 보안 정보를 저장 |
| SPD | 어떤 트래픽을 보호·통과·폐기할지 정하는 정책 저장 |

SPI는 암호키 자체가 아니다.

IKE(Internet Key Exchange)는 상대방을 인증하고 키와 보안 설정을 협상하여 SA를 생성·관리한다.

교재의 Phase 1·2는 IKEv1 기준이다.

| 단계 | 핵심 |
| --- | --- |
| Phase 1 | 안전한 협상 통로인 IKE SA 생성 |
| Phase 2 | 실제 데이터를 보호할 IPsec SA 협상 |

IKEv2는 이와 다른 교환 절차를 사용하므로, 모든 IKE가 Phase 1·2로 동작한다고 일반화하지 않는다.

### SECTION 30. 최신 네트워크 보안 동향


**연결 기출 Q418–Q423**

### 1. 보안 관리 기술 비교

| 기술 | 핵심 개념 | 기억할 키워드 |
| --- | --- | --- |
| ESM | 여러 보안 장비를 중앙에서 통합 관제·관리 | 보안 시스템 통합 관리 |
| SIEM | 보안 장비와 서버·응용프로그램 등의 로그를 수집하고 연관 분석하여 위협 탐지 | 로그 수집·상관분석 |
| SOAR | 여러 보안 도구를 연동하고 정해진 대응 절차를 자동으로 실행 | 대응 자동화 |
| NAC | 사용자·단말의 신원과 보안 상태를 검사하여 네트워크 접속 통제 | 접속 전 검사·격리 |
| PMS | 운영체제·소프트웨어 패치를 중앙에서 배포하고 적용 상태 관리 | 패치 통합 관리 |
| UTM | 방화벽·IPS·백신 등 여러 보안 기능을 하나의 장비에 통합 | 보안 기능 통합 |

ESM과 UTM의 차이:

- ESM: 여러 보안 장비를 한곳에서 관리한다.
- UTM: 여러 보안 기능을 한 장비에서 수행한다.

SIEM과 SOAR의 차이:

- SIEM: 로그를 분석해 “어떤 위협이 발생했는가?”를 판단한다.
- SOAR: 탐지 결과를 받아 “어떤 순서로 대응할 것인가?”를 실행한다.

```
방화벽·IPS·서버 등의 로그
           ↓
SIEM: 수집 → 상관분석 → 위협 탐지
           ↓
SOAR: 대응 절차에 따라 도구 연동
           ↓
IP 차단·단말 격리·담당자 알림
```

상관분석은 여러 기록을 연결해 의미를 찾는 것이다. 예를 들어 로그인 실패가 반복된 뒤 로그인 성공과 대량 자료 다운로드가 이어지면, 이를 연결해 계정 탈취를 의심한다.

### 2. NAC — 네트워크 접근 제어

내부 네트워크에 접속하려는 사용자와 단말을 확인하고, 보안 정책을 만족하는 경우에만 허용하는 기술이다.

```
단말 접속 요청
      ↓
사용자·단말 인증
      ↓
백신·패치 등 보안 상태 검사
      ├─ 적합 → 허용된 네트워크 접근
      └─ 미흡 → 차단 또는 격리 → 보완 후 재검사
```

| 기능 | 확인 내용 |
| --- | --- |
| 인증 | 허가된 사용자와 단말인가? |
| 보안 상태 검사 | 백신 설치·업데이트, 보안 패치 등 정책을 준수했는가? |
| 접근 통제 | 어느 네트워크와 자원까지 접근할 수 있는가? |
| 격리·보완 | 정책 미준수 단말을 분리하고 필요한 조치를 유도 |

접속 이후에도 단말 상태를 확인하여 접근 권한을 변경할 수 있다.

| 구현 방식 | 특징 |
| --- | --- |
| 에이전트 방식 | 단말에 프로그램을 설치하여 보안 상태를 상세하게 확인 |
| 에이전트리스 방식 | 단말에 전용 프로그램을 설치하지 않고 네트워크 장비 등을 이용해 통제 |

대표적인 통제 수단:

- 802.1X: 인증 결과에 따라 스위치·AP의 네트워크 접근을 허용.
- VLAN: 미인증·정책 미준수 단말을 격리 VLAN으로 분리.
- DHCP: IP 주소 할당을 통한 통제. 정적 IP 설정 등으로 우회될 수 있어 단독 통제에는 한계가 있다.

---

### 3. PMS — 패치 관리 시스템

여러 PC와 서버의 보안 패치를 중앙에서 관리하는 시스템이다.

```
패치 대상 확인 → 패치 검증 → 배포·설치 → 적용 결과 확인
```

- 목적: 패치 누락을 줄이고 알려진 취약점을 제거.
- 주요 기능: 패치 배포, 설치 일정 관리, 적용 여부 확인, 실패 장비 재처리.
- NAC와의 관계: NAC가 패치 미적용 단말을 찾아 격리하고, PMS가 패치를 적용하도록 연계할 수 있다.

---

### 4. 역추적 시스템 — Traceback

공격 트래픽과 연결 기록을 거꾸로 따라가 공격의 발생 지점이나 경유지를 추적하는 기술이다.

| 구분 | 분석 대상 |
| --- | --- |
| 호스트 기반 역추적 | 각 호스트의 접속 기록·로그 |
| 네트워크 기반 역추적 | 패킷·트래픽 흐름·연결 정보 |

공격자가 여러 경유지를 거치거나 출발지 IP를 위조한 경우, 화면에 보이는 출발지 IP만으로 실제 공격자를 판단하기 어렵기 때문에 사용한다.

단, 역추적으로 실제 사람의 신원이나 물리적 위치까지 반드시 확인할 수 있는 것은 아니다.

---

### 5. SDN — 소프트웨어 정의 네트워킹

네트워크의 경로를 결정하는 제어 기능과 실제 패킷을 전달하는 기능을 분리하여 소프트웨어로 관리하는 기술이다.

```
SDN 컨트롤러: 전달 규칙 결정
               ↓
스위치: 규칙에 따라 패킷 전달
```

- 제어 평면: 패킷을 어디로 보낼지 결정.
- 데이터 평면: 결정된 규칙에 따라 실제 패킷 전달.
- OpenFlow: 컨트롤러와 스위치 사이에서 전달 규칙을 제어하는 대표적인 프로토콜.
- 효과: 네트워크 설정과 보안 정책을 중앙에서 유연하게 적용.

## FTP 기본 구조

FTP는 파일을 주고받을 때 TCP 연결 두 개를 사용한다.

| 연결 | 기본 포트 | 역할 |
| --- | --- | --- |
| 제어 연결 | TCP 21 | 로그인, 명령 전달, 전송 요청 |
| 데이터 연결 | 별도 포트 | 파일 내용이나 디렉터리 목록 전송 |

제어 연결은 명령을 주고받는 통로이고, 데이터 연결은 실제 데이터를 옮기는 통로다.

## 능동 모드와 수동 모드

두 모드의 차이는 데이터 연결을 누가 먼저 여느냐다.

| 구분 | 능동 모드(Active) | 수동 모드(Passive) |
| --- | --- | --- |
| 데이터 연결을 여는 쪽 | 서버가 클라이언트로 연결 | 클라이언트가 서버로 연결 |
| 제어 연결 | 클라이언트가 서버 TCP 21번에 연결 | 동일 |
| 데이터 연결 | 서버가 클라이언트 쪽으로 접속 | 서버가 포트를 알려주고, 클라이언트가 접속 |
| 방화벽·NAT 환경 | 서버에서 클라이언트로 들어오는 연결이 막힐 수 있음 | 클라이언트가 연결을 시작하므로 비교적 잘 통과 |

### 능동 모드 흐름

```
클라이언트 ──제어 연결──> 서버:21
클라이언트 ──PORT 명령──> 서버: 데이터 연결에 쓸 클라이언트 포트 전달
서버       ──데이터 연결──> 클라이언트
```

서버가 클라이언트 쪽으로 새 연결을 시작한다. 클라이언트가 방화벽이나 NAT 뒤에 있으면 연결이 차단될 수 있다.

### 수동 모드 흐름

```
클라이언트 ──제어 연결──> 서버:21
클라이언트 ──PASV 명령──> 서버
서버       ──응답────────> 데이터 연결용 서버 포트 안내
클라이언트 ──데이터 연결──> 서버의 안내된 포트
```

클라이언트가 데이터 연결도 시작하므로 방화벽·NAT 환경에서 주로 사용된다. 서버 쪽에서는 데이터용 포트가 열려 있어야 한다.

## 보안상 주의

기본 FTP는 계정 정보와 파일을 암호화하지 않고 전송한다. 암호화가 필요하면 FTPS 또는 SFTP를 사용한다.

- FTPS: FTP에 TLS를 적용
- SFTP: SSH를 이용한 파일 전송 방식. FTP와는 별개의 프로토콜이지만, 안전한 파일 전송 용도로 쓰임

기억할 점: 능동 모드는 서버가 클라이언트로 접속하고, 수동 모드는 클라이언트가 서버로 접속한다.

### SECTION 32. 이메일 보안

## 1. 이메일 전달 구조

메일은 보통 다음 흐름으로 이동합니다.

```
보내는 사람
  → MUA
  → MSA
  → MTA
  → 받는 쪽 MTA
  → MDA
  → 메일함
  → MRA
  → 받는 사람의 MUA
```

| 구성요소 | 역할 |
| --- | --- |
| MUA | 사용자가 메일을 작성하고 읽는 프로그램. 예: Outlook |
| MSA | 사용자가 보낸 메일을 접수해 발신 메일 서버로 전달 |
| MTA | 메일 서버 사이에서 메일을 전달하거나 중계 |
| MDA | 도착한 메일을 수신자의 메일함에 저장 |
| MRA | 메일함의 메일을 사용자에게 가져오거나 전달 |
| MS | 메일 서버를 통틀어 부르는 말 |

메일을 보낼 때는 주로 SMTP를 사용하고, 메일함에서 메일을 가져올 때는 POP3 또는 IMAP을 사용합니다.

## 2. SMTP

SMTP는 메일을 보내고 서버 사이에서 전달하는 프로토콜입니다. 메일 수신자가 누구인지 확인하고, 메일 내용을 전달합니다.

주요 명령은 다음과 같습니다.

| 명령 | 의미 |
| --- | --- |
| HELO / EHLO | 클라이언트가 서버에 인사하고 연결을 시작 |
| MAIL FROM | 발신자 주소 지정 |
| RCPT TO | 수신자 주소 지정 |
| DATA | 메일 본문 전송 시작 |
| QUIT | 연결 종료 |
| RSET | 현재 메일 전송 작업 초기화 |
| VRFY | 사용자 주소 확인 요청 |

SMTP 자체는 메일 내용을 암호화하지 않습니다. 따라서 전송 구간을 보호하려면 TLS를 사용하는 방식이 필요합니다.

## 3. POP3와 IMAP

둘 다 메일을 수신할 때 쓰지만, 메일을 다루는 방식이 다릅니다.

| 구분 | POP3 | IMAP |
| --- | --- | --- |
| 기본 방식 | 메일을 사용자 기기로 내려받음 | 서버의 메일함을 서버에 둔 채 접근 |
| 여러 기기에서 사용 | 동기화에 불편할 수 있음 | 여러 기기에서 상태를 동기화하기 편함 |
| 주 용도 | 한 기기에서 메일을 내려받아 확인 | 여러 기기에서 메일함을 관리 |

## 4. PGP

PGP는 이메일의 기밀성, 무결성, 발신자 인증을 제공하는 방식입니다.

- 기밀성: 메일 본문은 대칭키로 암호화하고, 그 세션키를 수신자의 공개키로 보호합니다. 수신자는 개인키로 세션키를 복원한 뒤 본문을 복호화합니다.
- 발신자 인증과 무결성: 메일의 해시값을 만든 뒤 발신자의 개인키로 서명합니다. 수신자는 발신자의 공개키로 서명을 확인합니다.
- 메일 호환성: 암호화된 데이터는 전자우편 시스템에서 다루기 쉽도록 Radix-64 형식으로 변환할 수 있습니다.
- PGP는 중앙 인증기관에 의존하기보다 사용자 사이의 신뢰 관계를 이용합니다.

## 5. S/MIME

S/MIME은 이메일에 암호화와 전자서명을 적용하는 표준입니다. 공개키 인증서 기반으로 동작합니다.

| 기능 | 목적 |
| --- | --- |
| 전자서명 | 발신자 확인과 메일 변조 여부 확인 |
| 메시지 암호화 | 수신자만 내용을 읽을 수 있게 보호 |
| 압축 | 메시지 크기 감소 |
| 이메일 호환성 | 암호화된 내용을 이메일로 전송할 수 있는 형식으로 변환 |

## 6. PGP와 S/MIME 비교

| 구분 | PGP | S/MIME |
| --- | --- | --- |
| 공통점 | 이메일 암호화와 전자서명 지원 | 이메일 암호화와 전자서명 지원 |
| 신뢰 확인 방식 | 사용자 간 신뢰 관계 중심 | 인증기관이 발급한 인증서 중심 |
| 활용 경향 | 개인 사용자 간 보안 메일 | 기업·조직의 표준 이메일 보안 |

## 핵심 흐름

```
메일 전송: MUA → SMTP/MSA → MTA → MDA → 메일함
메일 수신: 메일함 → POP3 또는 IMAP → MUA

이메일 보안:
전자서명 = 누가 보냈는지 확인 + 변조 여부 확인
암호화   = 허가된 수신자만 내용 확인
```

# 웹 보안 핵심 정리

## 1. SSL/TLS: 통신 내용을 보호하는 기술

HTTP만 사용하면 통신 내용을 중간에서 읽거나 바꿀 수 있습니다. TLS는 클라이언트와 서버 사이에 안전한 통신 경로를 만들어 이를 막습니다. HTTPS는 HTTP를 TLS로 보호하는 방식입니다.

```
HTTP 메시지
    ↓
TLS가 암호화·무결성 보호
    ↓
TCP를 통해 전송
```

TLS가 제공하는 핵심은 세 가지입니다.

| 기능 | 의미 |
| --- | --- |
| 기밀성 | 중간에서 데이터를 읽지 못하도록 암호화 |
| 무결성 | 전송 중 데이터가 바뀌었는지 확인 |
| 인증 | 인증서 등을 통해 접속한 서버가 누구인지 확인 |

TLS는 크게 두 과정으로 이해하면 됩니다.

1. 핸드셰이크: 서로 사용할 암호 방식에 합의하고, 서버 인증서를 검증하며, 통신에 쓸 키를 만듭니다.
2. 레코드 전송: 만들어진 키로 실제 데이터를 보호하여 주고받습니다.

다음 Handshake, Alert, Record 등의 관계도 이 틀로 보면 됩니다. Handshake는 보안 연결을 준비하고, Record는 실제 메시지를 실어 나르며, Alert는 오류나 종료 같은 상태를 알립니다. 자료의 ChangeCipherSpec은 주로 과거 TLS 버전의 절차를 설명할 때 등장합니다.

주의할 점은 TLS가 적용되어도 웹 서버 자체의 SQL Injection이나 CSRF 취약점까지 해결되지는 않는다는 것입니다.

## 2. SQL Injection: 입력값이 SQL 명령으로 실행되는 공격

애플리케이션이 사용자 입력을 SQL 문장에 그대로 이어 붙이면, 공격자가 입력한 글자가 데이터가 아닌 SQL 명령의 일부로 해석될 수 있습니다.

```
사용자 입력
    ↓
서버가 SQL 문장에 그대로 결합
    ↓
DB가 공격자가 의도한 SQL까지 실행
```

그 결과 인증 우회, 데이터 조회·변경·삭제 등이 발생할 수 있습니다.

다음 유형은 다음처럼 구분하면 됩니다.

| 유형 | 핵심 |
| --- | --- |
| 일반적인 SQL Injection | 입력값으로 원래 SQL의 조건이나 동작을 바꿈 |
| UNION 방식 | 다른 조회 결과를 기존 조회 결과에 붙여 데이터를 빼냄 |
| 오류 기반 | DB 오류 메시지에 드러나는 정보를 이용 |
| Blind SQL Injection | 화면에 결과가 직접 나오지 않아도 참·거짓 반응이나 응답 시간 차이로 정보를 추론 |

핵심 방어책은 준비된 SQL 문장과 매개변수 바인딩입니다. 이렇게 하면 입력값이 SQL 명령과 분리되어 데이터로 처리됩니다. 입력 검증, DB 계정의 최소 권한, 상세 오류 메시지 숨기기는 추가 방어책입니다.

## 3. SSRF: 서버를 대신 요청하게 만드는 공격

SSRF(Server-Side Request Forgery)는 공격자가 웹 서버에 URL을 입력시키고, 웹 서버가 그 주소로 요청을 보내게 하는 공격입니다.

```
공격자 → 웹 서버에 URL 전달
              ↓
         웹 서버가 해당 URL에 접속
              ↓
       내부 서버·내부 자원에 접근 가능
```

예를 들어 “URL을 입력하면 이미지를 가져오는 기능”이 있다고 해 봅시다. 서버가 주소를 제한 없이 받아들이면, 공격자는 외부에서 직접 접근할 수 없는 내부 주소를 서버가 대신 방문하게 만들 수 있습니다. 그래서 SSRF의 핵심은 공격자가 서버의 네트워크 접근 권한을 빌려 쓰는 것입니다.

주요 대응책은 다음과 같습니다.

- 서버가 접속할 수 있는 목적지를 허용 목록으로 제한
- 사설 IP, 루프백 주소, 내부 관리 주소 등으로의 요청 차단
- 주소가 다른 곳으로 바뀌는 리다이렉트와 DNS 재해석까지 검사
- 서버 자체의 내부망 접근 권한을 최소화

## 4. CSRF와 XSS: 헷갈리기 쉬운 웹 공격

자료의 웹 공격을 구분할 때는 “누구의 무엇을 악용하는가”를 보면 편합니다.

| 공격 | 악용하는 것 | 핵심 결과 |
| --- | --- | --- |
| CSRF | 로그인된 사용자의 브라우저와 인증 상태 | 사용자가 의도하지 않은 요청을 서버에 보냄 |
| XSS | 웹페이지에 삽입된 악성 스크립트 | 다른 사용자의 브라우저에서 스크립트가 실행됨 |
| SSRF | 웹 서버의 요청 기능과 네트워크 접근 권한 | 서버가 공격자가 지정한 주소로 요청함 |
| SQL Injection | SQL 문장에 섞인 사용자 입력 | DB가 의도하지 않은 SQL을 실행함 |

CSRF는 “로그인된 사용자를 속여 요청시키는 것”, SSRF는 “서버를 속여 요청시키는 것”으로 기억하면 구분하기 쉽습니다.

CSRF 방어에는 CSRF 토큰, SameSite 쿠키, 중요한 작업의 재인증 등이 쓰입니다. XSS 방어에는 출력 시 문맥에 맞는 인코딩과 안전한 DOM 처리 등이 중요합니다.

## 5. WAF: 웹 요청을 검사하는 방어 장치

WAF(Web Application Firewall)는 웹 애플리케이션 앞에서 HTTP 요청과 응답을 살펴보고, 설정된 규칙에 따라 의심스러운 요청을 차단하는 장치입니다.

```
사용자 → WAF → 웹 서버 → DB
          검사
```

일반 방화벽이 주로 IP, 포트, 프로토콜 등을 기준으로 통신을 제어한다면, WAF는 URL, 요청 매개변수, HTTP 본문처럼 웹 애플리케이션의 내용을 살펴볼 수 있습니다. SQL Injection이나 XSS 패턴을 탐지하는 데 사용됩니다.

다만 WAF 규칙만으로 애플리케이션의 취약점이 없어지는 것은 아닙니다. SQL Injection은 서버 코드에서 매개변수 바인딩으로 고치고, WAF는 그 위에 추가하는 방어 수단으로 이해하면 됩니다.

## 한 번에 연결하기

```
사용자 ── TLS/HTTPS ── WAF ── 웹 애플리케이션 ── DB
          통신 보호       요청 검사       입력 처리         데이터 저장
                                        │
                                        └─ 외부·내부 URL 요청 기능
                                             → SSRF 주의
```

시험용으로는 이렇게 잡으면 됩니다: TLS는 전송 구간 보호, WAF는 웹 요청 검사, SQL Injection은 DB 명령 오염, CSRF는 사용자 브라우저 악용, SSRF는 서버의 요청 기능 악용입니다.

### SECTION 34. DHCP와 DNS 보안


**연결 기출 Q488–Q494**

# DHCP·DNS·데이터베이스 보안 요약

이 내용은 세 부분으로 이어집니다. DHCP가 단말에 네트워크 설정을 주고, DNS가 이름을 IP 주소로 바꾸며, 데이터베이스 보안은 저장된 정보에 누가 접근하고 무엇을 알 수 있는지 통제합니다.

## 1. DHCP: 단말에 네트워크 설정을 자동으로 주는 기능

DHCP는 단말이 네트워크에 접속할 때 IP 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버 주소 등을 자동으로 할당합니다. UDP를 사용하며, 서버는 67번 포트, 클라이언트는 68번 포트를 사용합니다.

| 순서 | 메시지 | 의미 |
| --- | --- | --- |
| 1 | Discover | 클라이언트가 DHCP 서버를 찾음 |
| 2 | Offer | 서버가 사용 가능한 IP 등을 제안 |
| 3 | Request | 클라이언트가 제안받은 주소를 요청 |
| 4 | ACK | 서버가 할당을 확정 |

흐름은 `Discover → Offer → Request → ACK`, 앞글자로 DORA입니다. 주소를 영구히 주는 것이 아니라 임대 기간을 정해 할당하며, 클라이언트는 기간이 끝나기 전에 갱신합니다.

보안상 핵심은 클라이언트가 받은 설정을 신뢰하고 사용한다는 점입니다. 공격자가 가짜 DHCP 서버로 응답하면 잘못된 게이트웨이나 DNS 서버를 배포해 트래픽을 우회시킬 수 있습니다. 반대로 주소 풀을 고갈시키는 공격은 정상 단말이 IP를 받지 못하게 만듭니다.

## 2. DNS: 이름을 IP 주소로 바꾸는 기능

DNS는 `example.com` 같은 이름에 대응하는 IP 주소를 찾습니다. 일반적인 조회에서는 UDP 53번 포트를 주로 사용하고, 필요한 경우 TCP 53번도 사용합니다.

이름을 찾는 과정에서 역할을 구분하면 쉽습니다.

- 로컬 캐시와 `hosts` 파일: 이미 알고 있는 이름·주소 정보를 확인합니다. 실제 조회 순서는 운영체제 설정에 따라 달라집니다.
- 재귀 DNS 서버(리졸버): 사용자를 대신해 답을 찾아오고, 결과를 일정 시간 캐시에 저장합니다.
- 권한 DNS 서버: 자신이 담당하는 도메인의 DNS 레코드에 대해 답합니다.

자주 나오는 레코드는 다음과 같습니다.

| 레코드 | 의미 |
| --- | --- |
| A | 이름 → IPv4 주소 |
| AAAA | 이름 → IPv6 주소 |
| MX | 해당 도메인의 메일 서버 |
| NS | 해당 도메인을 담당하는 네임서버 |
| PTR | IP 주소 → 이름을 조회할 때 사용 |
| TXT | 문자열 정보 저장 |

DNS 보안의 핵심 문제는 잘못된 주소를 정상 답변처럼 믿게 만드는 것입니다.

- DNS 스푸핑: 위조된 DNS 응답을 보내 사용자를 다른 주소로 유도합니다.
- DNS 캐시 포이즈닝: 재귀 DNS 서버의 캐시에 잘못된 정보를 저장시켜, 이후 여러 사용자가 잘못된 답을 받게 합니다.
- `hosts` 파일 변조: 단말에 저장된 이름·주소 대응 관계를 바꿔 특정 사이트를 다른 IP로 연결합니다.

DNSSEC은 DNS 응답의 전자서명을 검증해 출처와 무결성을 확인하는 기술입니다. DNS 응답 내용을 암호화해 숨기는 기술은 아니며, DNS 서버를 대상으로 한 서비스 거부 공격까지 해결하지는 않습니다.

### SECTION 35. 데이터베이스 보안


**연결 기출 Q495–Q504**

## 데이터베이스 보안: 조회 권한과 추론까지 통제

DB 보안은 단순히 “테이블을 볼 수 있나”에서 끝나지 않습니다. 허용된 조회 결과를 조합해 금지된 정보를 알아낼 수도 있기 때문입니다.

예를 들어 직원별 급여 조회는 금지했지만 부서 평균 급여와 특정 직원을 제외한 평균 급여를 모두 제공한다면, 두 결과를 비교해 그 직원의 급여를 추정할 수 있습니다.

| 개념 | 핵심 |
| --- | --- |
| 집성(Aggregation) | 낮은 등급의 정보 여러 개를 모아 민감한 정보를 알아냄 |
| 추론(Inference) | 허용된 데이터나 통계 결과를 분석해 공개되지 않은 값을 유추함 |

대응할 때는 결과를 무조건 차단하는 것만이 아니라, 소수 인원에 대한 통계 제한, 조회 결과의 조합 제한, 필요한 범위만 공개하는 방식 등을 사용합니다.

### 접근 통제와 뷰

뷰(View)는 기본 테이블을 바탕으로 만든 가상 테이블입니다. 사용자에게 원본 테이블 전체 권한을 주는 대신, 필요한 행이나 열만 보이도록 뷰를 제공할 수 있습니다. 뷰가 있다고 자동으로 안전해지는 것은 아니므로 원본 테이블 권한과 뷰 권한을 함께 관리해야 합니다.

- `GRANT`: 사용자나 역할에 권한 부여
- `REVOKE`: 부여한 권한 회수
- DBA 권한: 다른 사용자와 데이터에 광범위하게 영향을 줄 수 있으므로 최소한으로 부여

### 저장 데이터의 암호화

DB 암호화는 먼저 “어디에서 암호화하느냐”로 나누면 이해하기 쉽습니다.

| 방식 | 암호화가 일어나는 곳 | 핵심 특징 |
| --- | --- | --- |
| Plug-in | DB 서버에 설치한 암호화 모듈 | DBMS와 연동해 특정 컬럼을 암호화. DB 서버에 추가 부담이 생길 수 있음 |
| API | 애플리케이션 | 앱이 데이터를 암호화한 뒤 DB에 저장. DB 서버 부담은 적지만 앱 수정이 필요하고, DB가 암호문 내용을 직접 처리하기 어려움 |
| TDE | DBMS 내부 | DB 파일을 저장할 때 자동 암호화하고 읽을 때 복호화. 앱 수정이 거의 필요 없음 |
| 파일 암호화 | 운영체제·파일 시스템 | DB 파일 자체를 암호화. DB뿐 아니라 다른 파일에도 적용 가능하지만 OS에 의존함 |
| Hybrid | Plug-in + API | 두 방식을 결합해 필요한 구간에 적용. 구성과 비용 부담이 커짐 |

### 컬럼 암호화와 파일 암호화의 차이

- 컬럼 암호화는 주민등록번호처럼 특정 값만 보호한다. Plug-in과 API 방식이 여기에 해당한다.
- TDE와 파일 암호화는 저장된 DB 파일을 보호한다. 저장장치나 백업 파일이 유출됐을 때 유용하다.
- TDE를 쓰더라도 권한 있는 사용자가 DB에 접속해 조회하면 평문을 볼 수 있다. 따라서 접근 권한 관리와 감사 로그도 함께 필요하다.

시험에서는 `Plug-in = DB 서버`, `API = 애플리케이션`, `TDE = DBMS의 저장 단계`, `파일 암호화 = OS·파일 시스템`으로 위치를 먼저 구분하면 됩니다.

### SECTION 36. 전자상거래 보안


**연결 기출 Q505–Q518**

전자상거래에서는 결제 정보를 보호하면서 거래 당사자가 누구인지 확인해야 합니다. 핵심 요구사항은 다음 네 가지입니다.

| 요구사항 | 뜻 |
| --- | --- |
| 기밀성 | 카드번호·결제 정보가 제3자에게 노출되지 않음 |
| 무결성 | 주문·결제 내용이 전송 중 바뀌지 않음 |
| 인증 | 고객과 가맹점의 신원을 확인함 |
| 부인 방지 | 거래 후 자신이 수행한 거래를 부인하기 어렵게 함 |

SET(Secure Electronic Transaction)은 카드 결제를 안전하게 처리하기 위한 프로토콜입니다. 등장인물의 역할을 먼저 구분하면 이해하기 쉽습니다.

| 구성 요소 | 역할 |
| --- | --- |
| 카드 소지자 | 상품을 구매하고 결제를 요청 |
| 가맹점 | 주문을 받고 결제를 진행 |
| 발급사 | 고객에게 카드를 발급한 금융기관 |
| 매입사 | 가맹점의 카드 거래를 처리하는 금융기관 |
| 결제 게이트웨이 | 가맹점과 금융기관 사이에서 결제 승인 처리 |
| 인증기관(CA) | 거래 참여자의 인증서 발급 |

거래 흐름은 `고객의 주문 → 가맹점의 결제 요청 → 결제 게이트웨이·금융기관의 승인 → 결과 전달`로 기억하면 됩니다.

SET의 핵심은 주문 정보와 결제 정보를 구분해 전달하는 것입니다. 가맹점은 주문을 처리하는 데 필요한 정보를 보고, 카드 결제 정보는 결제 처리 주체가 다룹니다. 전자서명과 인증서를 이용해 거래 내용과 참여자의 신원을 검증합니다.

### SECTION 37. 침해사고대응(디지털 포렌식)


 **연결 기출 Q519–Q525**

## 5. 디지털 포렌식과 침해사고 대응

디지털 포렌식은 사고가 난 시스템에서 디지털 증거를 수집·분석해 무슨 일이 있었는지 밝히는 과정입니다. 침해사고 대응에서는 피해 범위와 공격 경로를 파악하고, 복구와 재발 방지에 필요한 근거를 확보합니다.

자료의 일반적인 공격 흐름은 다음처럼 연결됩니다.

`대상 선정 → 취약점 수집·선정 → 취약점 악용 → 권한 획득 → 백도어 설치·다른 시스템 공격 → 흔적 삭제 시도`

이 흐름은 공격을 따라 하라는 절차가 아니라, 조사할 때 어느 단계의 흔적이 남았을지 찾는 틀입니다. 예를 들어 권한 획득 흔적은 계정·인증 기록에서, 백도어 흔적은 파일·프로세스·네트워크 기록에서 확인합니다.

CERT는 침해사고를 접수하고 분석·대응하며, 피해 복구와 예방 활동을 지원하는 사고 대응 조직입니다.

## 6. 증거를 다룰 때 가장 중요한 원칙

디지털 증거는 수집 과정에서 바뀌기 쉽습니다. 따라서 원본을 보존하고, 누가 언제 어디서 어떤 방법으로 증거를 다뤘는지 기록해야 합니다.

| 원칙 | 실무에서 뜻하는 것 |
| --- | --- |
| 원본 보존 | 원본을 함부로 분석하지 않고 사본을 만들어 조사 |
| 무결성 확인 | 수집 전후 해시값 등을 비교해 변경 여부 확인 |
| 관리 연속성(Chain of Custody) | 증거의 수집·이동·보관·분석 담당자와 시간을 기록 |
| 재현 가능성 | 같은 자료와 방법으로 분석했을 때 결과를 확인할 수 있어야 함 |
| 적법성 | 허용된 범위와 절차에 따라 증거를 수집 |

특히 관리 연속성은 “이 증거가 처음 발견된 그 증거가 맞고, 중간에 누군가 바꾸지 않았다”는 점을 설명하는 기록입니다.

## 7. 디지털 포렌식 절차와 종류

자료의 절차는 다음 순서로 정리할 수 있습니다.

`사전 준비 → 증거 수집·획득 → 보존 및 검증 → 조사·분석 → 결과 보고·제시`

시험에서는 각 단계의 목적을 구분하는 것이 중요합니다. 수집 단계에서는 필요한 자료를 확보하고, 보존 단계에서는 원본 변경을 막고, 분석 단계에서는 사건의 시간순 흐름과 원인을 밝힙니다. 마지막에는 다른 사람이 검토할 수 있도록 방법과 결과를 문서화합니다.

조사 대상에 따라 디스크 포렌식, 네트워크·인터넷 포렌식, 모바일 포렌식, 데이터베이스 포렌식 등으로 나뉩니다. 살아 있는 시스템의 메모리·실행 중인 프로세스처럼 전원을 끄면 사라질 수 있는 정보는 라이브 포렌식의 대상입니다.

시험용으로 한 줄로 묶으면: `SET은 안전한 전자결제`, `CERT는 사고 대응 조직`, `디지털 포렌식은 증거를 보존하며 사고를 재구성하는 과정`입니다.

- 근절은 악성코드 제거만이 아니라 침입 경로 차단·자격 증명 교체·취약점 수정까지 포함한다. 복구 후에는 같은 공격이 재발하는지 관찰한다.

#### 포렌식의 증거성과 절차

- 디지털 증거는 **원본 보존, 무결성 검증, 수집·이동·분석 담당자와 시각 기록(보관 연속성)**이 중요하다. 해시값은 사본 일치성을 확인하는 자료 중 하나다.
- 휘발성이 높은 메모리·실행 중 네트워크 상태는 전원을 끄면 사라질 수 있다. 현장에서는 수집 순서와 수집 도구가 원본에 미치는 영향을 기록한다.

### SECTION 39. 정보보호 거버넌스와 관리 체계 수립


# 정보보호 거버넌스와 관리체계

정보보호 거버넌스는 조직의 목표에 맞춰 정보보호의 방향과 책임을 정하고, 그 결과를 감독하는 체계입니다. 정보보호 관리체계(ISMS)는 그 방향을 실제 정책과 절차로 만들고 운영·점검·개선하는 체계입니다.

## 1. ISO/IEC 27000 시리즈

| 표준 | 핵심 내용 |
| --- | --- |
| 27000 | 시리즈의 개요와 용어 |
| 27001 | ISMS가 갖춰야 할 요구사항. 인증의 기준이 되는 표준 |
| 27002 | 정보보호 통제를 선택하고 적용할 때 참고하는 실무 지침 |
| 27003 | ISMS 구축·구현 지침 |
| 27004 | 정보보호 성과 측정과 평가 지침 |
| 27005 | 정보보호 위험관리 지침 |
| 27014 | 정보보호 거버넌스의 개념과 원칙 |
| 27017 | 클라우드 환경의 정보보호 통제 지침 |
| 27018 | 공용 클라우드에서 처리하는 개인정보 보호 지침 |

시험에서 먼저 구별할 것은 27001은 ‘요구사항’, 27002는 ‘통제 지침’, 27005는 ‘위험관리’, 27014는 ‘거버넌스’라는 점입니다.

## 2. 정보보호 정책의 체계

조직의 정보보호 문서는 큰 방향에서 구체적인 작업 방법으로 내려갑니다.

```
정책을 바탕으로 표준·지침·절차를 마련
왜·무엇을 지킬까 → 반드시 지킬 기준 → 권장하는 방법 → 실제 작업 순서
```

| 구분 | 의미 | 예 |
| --- | --- | --- |
| 정책(Policy) | 조직의 정보보호 목표와 기본 원칙을 선언 | “중요 정보는 접근 권한을 통제한다” |
| 표준(Standard) | 정책을 지키기 위해 반드시 따라야 할 구체적 기준 | “관리자 계정에는 다중 인증을 적용한다” |
| 지침(Guideline) | 기준을 구현할 때 참고하는 권장 방법 | “인증 앱 사용을 권장한다” |
| 절차(Procedure) | 담당자가 실제로 수행할 단계와 순서 | “신청 → 승인 → 권한 부여 → 기록” |

기준선(Baseline)은 시스템에 공통으로 적용할 최소 보안 수준입니다. 예를 들어 새 서버를 설치할 때 기본적으로 적용할 계정·로그·설정 기준이 이에 해당합니다.

## 3. 정보보호 조직의 역할

| 역할 | 하는 일 |
| --- | --- |
| 최고경영자 | 정보보호 방침과 자원을 승인하고 조직 차원의 책임을 짐 |
| 정보보호 관리자 | 정책·표준·대책을 수립하고 운영을 총괄 |
| 데이터 관리자 | 데이터의 정확성·무결성·유용성을 유지하고 관련 책임을 관리 |
| 프로세스 관리자 | 담당 업무와 정보시스템에 필요한 보호 대책을 운영 |
| 기술지원 인력 | 요구된 보안 대책을 시스템에 구현하고 유지 |
| 사용자 | 정해진 정책과 절차를 준수 |
| 정보시스템 감사자 | 정책과 통제가 실제로 지켜지는지 독립적으로 점검하고 보고 |

역할을 나누는 이유는 “누가 결정하고, 누가 실행하며, 누가 확인하는가”를 분명히 하기 위해서입니다.

## 4. ISMS 운영: PDCA

| 단계 | 할 일 |
| --- | --- |
| Plan(계획) | 보호할 자산과 위험을 파악하고 정책·목표·대책을 수립 |
| Do(실행) | 정한 대책과 절차를 적용하고 운영 |
| Check(점검) | 운영 결과를 측정·감사해 계획대로 작동하는지 확인 |
| Act(개선) | 사고, 점검 결과, 환경 변화를 반영해 대책을 고침 |

핵심은 한 번 구축하고 끝내는 것이 아니라 `계획 → 실행 → 점검 → 개선 → 다시 계획`을 반복하는 것입니다.

### SECTION 40. 정보보호 위험관리



# 위험관리 핵심 정리

위험관리는 조직의 자산에 어떤 문제가 생길 수 있는지 파악하고, 그 위험을 평가한 뒤 적절한 보호대책을 선택하는 과정이다.

## 1. 위험을 이루는 요소

| 요소 | 뜻 | 예시 |
| --- | --- | --- |
| 자산 | 조직이 보호해야 할 것 | 고객정보, 서버, 업무 서비스 |
| 위협 | 자산에 손실을 일으킬 수 있는 원인이나 사건 | 랜섬웨어, 화재, 내부자의 정보 유출 |
| 취약점 | 위협이 실제 피해로 이어질 수 있게 하는 약점 | 미적용 보안 패치, 약한 비밀번호 |
| 위험 | 위협이 취약점을 이용해 자산에 피해를 줄 가능성과 그 영향 | 패치되지 않은 서버가 공격받아 서비스가 중단될 위험 |

흐름으로 보면 다음과 같다.

`보호할 자산 → 위협과 취약점 파악 → 발생 가능성과 피해 규모 평가 → 보호대책 선택`

예를 들어 고객정보가 자산이고, 계정 탈취가 위협이며, 약한 비밀번호가 취약점이라면 고객정보 유출이 위험이다.

## 2. 위험 수준을 판단하는 방법

`위험 = 자산 가치 × 위협 수준 × 취약성`은 일부 평가 방법의 개념식이며, 모든 위험평가에 적용하는 보편적 계산식은 아니다. 실제 평가에서는 각 요소를 정확한 숫자로 계산하기보다, 발생 가능성과 피해 규모를 높음·중간·낮음 등으로 평가하기도 한다.

- 자산 가치가 클수록 같은 사고라도 피해가 커진다.
- 위협의 발생 가능성이 높을수록 위험이 커진다.
- 취약점이 많거나 심각할수록 공격이 성공할 가능성이 커진다.

## 3. 위험에 대응하는 네 가지 방법

| 대응 | 의미 | 예시 |
| --- | --- | --- |
| 위험 회피 | 위험을 만드는 활동 자체를 중단 | 위험한 서비스를 폐지 |
| 위험 감소 | 보호대책을 적용해 가능성이나 피해를 줄임 | 패치, 접근통제, 백업 |
| 위험 전가 | 손실의 일부를 다른 주체가 부담하게 함 | 보험 가입, 계약을 통한 책임 분담 |
| 위험 수용 | 남은 위험을 알고도 감수 | 대책 비용이 예상 피해보다 큰 경우 승인 후 유지 |

보호대책을 적용해도 위험이 완전히 0이 되지는 않는다. 대책을 적용한 뒤 남아 있는 위험이 잔여 위험이다. 조직은 이 잔여 위험을 다시 평가하고, 감당할 수 있는 수준인지 결정해야 한다.

## 4. 위험분석 방법

| 방법 | 특징 |
| --- | --- |
| 정량적 분석 | 사고 확률과 피해액을 금액·수치로 추정한다. 비교가 쉽지만 정확한 자료를 구하기 어렵다. |
| 정성적 분석 | 위험을 높음·중간·낮음처럼 등급으로 평가한다. 빠르고 적용하기 쉽지만 평가자의 판단이 개입된다. |

시험에서는 다음 관계를 구분하면 된다.

`잔여 위험 = 보호대책 적용 후 다시 평가한 위험`

즉, 위험관리의 목표는 모든 위험을 없애는 것이 아니라 조직이 수용 가능한 수준까지 줄이고, 남은 위험을 관리하는 것이다.

### SECTION 41. BCP/DRP



# BCP/DRP와 복구 시간 지표

이 단원은 “장애가 나면 무엇을, 얼마나 빨리 복구해야 하는가”로 연결해서 보면 이해하기 쉽습니다.

## 1. BCP와 DRP

| 구분 | 핵심 목적 | 범위 |
| --- | --- | --- |
| BCP (업무연속성계획) | 사고 중에도 핵심 업무를 계속하거나 빠르게 재개 | 인력, 업무 절차, 대체 장소, IT 시스템 등 조직 전체 |
| DRP (재해복구계획) | 장애가 난 IT 시스템과 데이터를 복구 | 서버, 네트워크, 데이터, 백업 등 |

DRP는 BCP를 실행하기 위한 IT 복구 계획입니다. 예를 들어 본사 전산실이 멈췄다면, DRP는 백업 서버와 데이터를 복구하고, BCP는 그동안 고객 업무를 어디서 어떻게 처리할지까지 정합니다.

## 2. BCP 수립 흐름

`프로젝트 범위·조직 구성 → 업무영향분석(BIA) → 복구전략 수립 → 계획 작성 → 교육·훈련·시험 → 유지·보수`

- BIA(업무영향분석): 업무가 중단됐을 때 시간에 따라 피해가 얼마나 커지는지 평가합니다. 이를 바탕으로 중요한 업무의 복구 우선순위와 허용 가능한 중단 시간을 정합니다.
- 복구전략: 대체 사업장, 백업 시스템, 인력과 연락 체계 등 실제 복구 방법을 정합니다.
- 시험과 유지: 계획이 문서상으로만 가능한지 확인하고, 조직이나 시스템이 바뀌면 갱신합니다.

## 3. 복구 시간 지표

사고 발생 시점을 기준으로 보면 다음과 같습니다.

`정상 운영 → 장애 발생 → 복구 작업 → 서비스 재개`

| 지표 | 뜻 | 기억할 점 |
| --- | --- | --- |
| MTBF | 고장과 다음 고장 사이의 평균 운영 시간 | 길수록 고장이 드묾 |
| MTTF | 고장까지의 평균 운영 시간 | 수리하지 않는 장치에 주로 사용 |
| MTTR | 고장 후 복구까지의 평균 시간 | 짧을수록 빨리 복구 |
| 가용성 | 필요한 때 서비스를 사용할 수 있는 정도 | MTBF ÷ (MTBF + MTTR) |

MTBF와 MTTF는 “얼마나 오래 버티는가”, MTTR은 “고장 나면 얼마나 빨리 고치는가”를 보는 값입니다.

## 4. 복구 목표: RTO와 RPO

| 지표 | 묻는 질문 | 예시 |
| --- | --- | --- |
| RTO (목표 복구 시간) | 서비스를 얼마 안에 복구할 것을 목표로 하는가? | RTO 2시간이면 2시간 안에 서비스 재개가 목표 |
| RPO (목표 복구 시점) | 데이터가 과거 어느 시점까지 되돌아가도 되는가? | RPO 30분이면 최대 30분치 데이터 손실을 허용 |

예를 들어 12시에 장애가 났고 RTO가 2시간, RPO가 30분이라면, 목표는 14시까지 서비스를 재개하고 데이터를 적어도 11시 30분 시점까지 복구하는 것입니다.

`RTO = 목표 복구 시간`. 최대 허용 중단시간(MTD/MTPD)과 구분하며, 업무 재개·검증에 필요한 시간도 고려해 더 짧게 설정한다.

`RPO = 데이터 손실 허용 범위`

두 목표를 짧게 잡을수록 백업, 이중화, 대체 설비에 더 많은 자원이 필요합니다.

## 5. 복구 사이트 선택

| 유형 | 준비 상태 | 복구 속도 | 비용 |
| --- | --- | --- | --- |
| 콜드 사이트 | 공간·전력 등 기본 시설 중심 | 느림 | 낮음 |
| 웜 사이트 | 일부 장비와 환경 준비 | 중간 | 중간 |
| 핫 사이트 | 운영에 필요한 설비와 데이터가 대부분 준비 | 빠름 | 높음 |
| 미러 사이트 | 주 사이트의 시스템·데이터를 거의 실시간으로 복제 | 매우 빠름 | 매우 높음 |

업무 중단을 거의 허용할 수 없다면 핫·미러 사이트가 적합하고, 복구에 시간이 있어도 되는 업무라면 웜·콜드 사이트를 고려합니다.

## 6. 재해 대응과 백업

재해가 발생하면 `비상 대응 → 피해 확인 → 복구 사이트 가동 → 데이터·시스템 복구 → 정상 운영 복귀` 순서로 진행합니다. 백업은 복구의 핵심이지만, 백업 파일만 있다고 서비스가 바로 재개되는 것은 아닙니다. 장비, 프로그램, 네트워크, 담당자와 복구 절차도 함께 준비해야 합니다.

백업 방식은 다음처럼 구분합니다.

| 방식 | 저장하는 내용 | 복구할 때 필요한 것 |
| --- | --- | --- |
| 전체 백업 | 모든 데이터 | 최근 전체 백업 |
| 차등 백업 | 마지막 전체 백업 이후 변경분 | 전체 백업 + 최근 차등 백업 |
| 증분 백업 | 마지막 백업 이후 변경분 | 전체 백업 + 이후 증분 백업 전부 |

시험에서는 특히 `BCP는 업무 지속`, `DRP는 IT 복구`, `RTO는 시간`, `RPO는 데이터 시점`, `MTTR은 실제 평균 복구 시간`을 구분하면 됩니다.
